## Режим работы

- Агент **read-write** в этом проекте: пишет код, данные, тесты, документацию.
- **CI локальному агенту запрещён (владелец, 2026-10-13).** CI запускает только
  владелец вручную. Агент **не поллит** прогоны, не ждёт их вердикта и не
  блокирует ими работу; push в `main` — конец обязанности агента по запуску.
  Автоматический ран по push — на усмотрение владельца (он же его отменяет).
- **Верификация агента — локальная машина**, но `game/run_tests.sh` — **один прогон
  в конце смены, перед публикацией** (владелец, 2026-10-27): в разработке полный
  гейт не запускается и шагом не проверяется. Стоит от 11 минут, спорит за порт
  9090 и X-дисплей с чужими сессиями, а решения по шагу не менял ни разу (зелёный
  GdUnit известен до прогона, T-178 красно на `main` независимо от правки). Шаг
  проверяется быстрыми проверками (§ «Верификация»), кадр одной сцены —
  `game/tools/shot_scene.gd` (без MCP-сервера и порта, ~0.4 с на съёмку).
  Зелёный гейт до push остаётся условием публикации — снято только его
  использование как цикла обратной связи. Прочие проверки — `gdtoolkit.linter`,
  `check_docs_links.py`; CI-вердикт добавляет владелец.
- Работа ведётся **только на `main`** (владелец, 2026-10-21, D-224): коммиты — прямо
  в `main`, feature-ветки не заводятся.
- Тесты — единственный обязательный способ верификации логики. UI не
  верифицируется headless-тестом, но и не откладывается: **ux-review делается
  машинным зрением агента** (секция «UX-review машинным зрением»). Звук и
  playtest остаются отложенными (deferred) — их нечем снять.

## UX-review машинным зрением (владелец, 2026-10-23)

ux-review — не шаг владельца и не предлог отложить задачу со словами «headless
не проверяет». UI-приёмку делает сам агент зрением по живому кадру:

1. **Кадр.** Поднять экран так, как его поднимает игрок — канальный съёмщик
   `game/tests/mcp/capture.py` (godot-mcp: `run_project` + `select_scene`/`game_eval`, —
   команда воспроизведения в [[CAPTURE-HELPER]]: `CAPTURE_SCENE=res://…/x.tscn
   CAPTURE_SETUP=<фикстура> python3 -m pytest tests/mcp/test_capture.py -q`), снять кадр
   в целевом разрешении в `tmp/shots/<screen>-<seq>.png` (пиксели в git не идут, D-185).
   Кадр состояния без `CAPTURE_SETUP` — другой кадр, а не нужный. Для шага
   разработки, когда нужен просто кадр одной сцены, — `game/tools/shot_scene.gd`
   (тот же `--state=` из `tools/capture/`, без сервера и порта); его кадр не входит
   в манифест и канон не доказывает — вердикт снимается pytest-путём.
2. **Сравнение.** Открыть кадр и макет-источник
   (`design/single_window_layout/all_screens_ui.png`) инструментом чтения
   изображений и разобрать поэлементно: состав, места, текст и иконки, пустые
   слоты, выход за кадр, читаемость.
3. **Вердикт в треде.** Кадр-доказательство, путь к макету, список расхождений с
   диспозицией (устранено / отложено с задачей / принято владельцем) и по каждой
   AC спеки — PASS/FAIL.
4. **Публикация — после ux-review, не до** (урок шага 2 UI-3). Кадр без вердикта
   и вердикт без кадра — review не пройден; «глазом не смотрел» не является
   основанием для FAIL-заключения «нельзя проверить».

Инструмент шагов 1–2 — скилл `.pi/skills/ui-grid-review`: одна адресная сетка на
кадр и на макет, кроп ячейки, «кто владеет этой областью» (`game/tools/ui_dump.gd`)
и дельта «до/после» (`scripts/ui_diff.py`) — расхождения в ней называются адресами
ячеек, а пиксельная мера остаётся сигналом, не вердиктом (D-228).

Съёмка поднимает GUI-окно: по одному процессу за раз, короткое время жизни,
чужие процессы не трогать (протокол зависших процессов).

## Безопасность команд (D-192)

Урок инцидента 2026-10-17 (агент удалил рабочее дерево опечаткой в абсолютном пути):

1. **Разрушительные команды** (`rm -rf`, `git clean -fdx`, `git reset --hard`, `mv`/перезапись
   поверх путей репо и `$HOME`) — только после **отдельной** проверки абсолютного пути
   (`pwd -P`, `test -d`, сверка префикса). Проверка и разрушение — **разные вызовы**;
   `mv` и `rm` в одной строке через `;`/`&&` **запрещены** (именно этот паттерн и сработал).
2. **Локальные артефакты вне git — не хранилище.** Всё, на что ссылается вердикт (замеры,
   скрипты, рендеры-доказательства), коммитится. gitignored-пиксели живут только вместе
   с картой и md5 (`reference/INDEX.md`) и проверяются `scripts/check_reference_index.py`.
3. **Перед удалением/перемещением в репо — `git status --ignored`**: не удалять молча то,
   чего нет в git (так погибли два канон-референса).

## Верификация

| Метод | Назначение |
| --- | --- |
| `godot --headless --path game --import` | Обновить кэш глобальных классов (после правки `class_name`) |
| `game/run_tests.sh` | Полный гейт: (1) GdUnit4 unit/integration/functional (headless); (2) MCP e2e (pytest + godot-mcp) |
| `godot ... GdUnitCmdTool.gd -a res://tests/<файл>.gd` | Запуск одного тест-файла |
| `Godot --path game -s tools/shot_scene.gd -- --scene=… [--state=…] --out=…` | Кадр ОДНОЙ сцены для шага разработки: без MCP-сервера и порта 9090, ~0.4 с; канон не доказывает |

**Быстрые проверки шага** (тем проверяется правка до гейта): один файл GdUnit
строкой выше; один pytest-узор (`pytest tests/mcp/test_capture.py -k <имя>`);
`python3 scripts/ui_grid.py --self-check` и `--verify` по кадру; `gdlint`/`gdformat`
по изменённым `.gd`; `python3 scripts/check_docs_links.py` по докам; кадр —
`tools/shot_scene.gd`. `game/run_tests.sh` в список не входит намеренно (§ «Режим
работы»): он прогон перед публикацией.

Код GdUnit4: `0` = pass, `101` = только orphan-предупреждения (гигиена, не
падение), `100` и прочие = реальные падения. **Политика гейта (CI-2, 2026-10-03):**
GdUnit4 `0`/`101` → GATE=0 (orphan = **warning**, не влияет на exit; красный =
только падения/регрессии); маппинг прописан явно в run_tests.sh.

**Readiness MCP — жёлтый (владелец, 2026-10-26, D-265).** `MCPError: игра не готова за
180 с …` (error в fixture readiness, T-172) — **жёлтый**, а не красный: среда, не
регрессия. Классификация машинная, не чтение лога глазами: pytest пишет `--junitxml`,
`scripts/classify_mcp_junit.py` возвращает `0` зелёный / `3` жёлтый (только readiness) /
`1` красный / `2` журнал не разобран; красный снимает **только** `3`, и только когда
красного нет вовсе. Неполный прогон (`сумма != collected`), неразобранный журнал,
`failure` и любой другой `error` красный не снимают. Жёлтый печатается поимённо
(`MCP READINESS: YELLOW — … - tests/mcp/…`); в гейт-артефакт обязана попасть строка
`MCP VERDICT:`. Сами-тест классификатора (`scripts/test_classify_mcp_junit.py`) — часть
гейта.

**Вердикт и протокол публикации (владелец, 2026-10-13, взамен CI-гейта;
переименован D-224):** вердикт =
**локальные тесты PASSED (GdUnit exit=0) + smoke по чек-листу PR + ревью
диффа владельцем в треде**. CI-раны не входят ни в промпты, ни в DoD, ни в
условия push. Компенсация снятого барьера: smoke-прогоны не сокращаются —
единственная автоматическая защита main; ревью диффа обязательно.
**Публикация (замена «мержа», D-224):** код/ассеты — только по явному «мержи»
владельца в сводке, и этим «мержи» становится **push в `main`**. Коммит в
локальный `main` публикацией не считается и слова владельца не требует. Docs —
агент пушит сам при `check_docs_links.py` pass. **Фича пушится после ux-review,
не до** (урок шага 2 UI-3: main нёс HUD с FAIL по AC7): ревью в
треде — часть вердикта, push до него — преждевременно. Отчётная форма гейт-блока —
локальный прогон с пометкой «local» (head_sha + статистика GdUnit + smoke).
- **Pull Request не заводится (владелец, 2026-10-17, D-201; механика уточнена
  D-224):** доступы/сертификаты прописаны на машине агента, поэтому `main`
  публикуется напрямую — `git push origin main`. GitHub-PR не создаётся, не ждётся
  и не является условием публикации; ревью диффа происходит в треде — сводка
  агента + дифф. Требование явного «мержи» для кода/ассетов это не отменяет:
  меняется механика, а не право агента решать.
- **Общая машина (то же D-201):** рабочий каталог могут делить несколько сессий,
  и чужой checkout с чужими грязными файлами **не трогается**. Если каталог занят,
  коммит в `main` собирается без переключения ветки — `git commit-tree` +
  `git push origin <sha>:main` (создавать для этого `git worktree` нельзя,
  см. «Git-конвенции»). Перед push — свежий
  `git ls-remote origin refs/heads/main`, и push обязан быть fast-forward
  (урок 2026-10-17: мерж совпал с активной сессией image-clone в том же worktree).

### Stuck-process protocol (раунд 13 §4)

Зависший процесс (Godot/Xvfb/MCP-сервер, занявший порт 9090 или X-дисплей, не
отвечает на гейт) — **не убивать молча**:

1. **Чужой PID (владелец/сессия не моя) → флаг, не убивать.** Диагностика:
   `ps -o pid,user,etime,cmd -p <PID>` (владелица, возраст). Чужой процесс
   фиксируется в отчёте (PID, пользователь, команда, что блокирует) — и гейт
   обходится свободным ресурсом (другой дисплей/порт, D-166-семья: раннер-
   среда, не код). `kill` чужого PID запрещён.
2. **Свой PID → убить** (только после проверки, что это мой процесс: `ps -o user`
   совпадает; age/команда совпадают с моим прогоном).
3. **> 4 часов → владелец репо.** Зависание старше 4 часов (свой или чужой)
   эскалируется владельцу репо (сообщение: PID, пользователь, команда, возраст,
   что блокирует, предположение причины). Это системный симптом (D-166-класс),
   не локальная проблема сессии.

## Git-конвенции

- Работа ведётся **только на `main`** (владелец, 2026-10-21, D-224): коммиты и push —
  в `main`; заводить ветку «чтобы потом смержить» не нужно.
- **`git worktree` агенту запрещён без явного задания владельца (владелец,
  2026-10-24).** Одно рабочее дерево — единственный checkout репо, ветка `main`.
  Не создавать worktree и не клонировать репо «чтобы не мешать чужой сессии»,
  «для мержа», «для гейта»: ни `git worktree add`, ни возня с чужими записями
  (`prune`, `remove`). Нужен второй checkout — спросить владельца. Мерж без
  переключения ветки собирается plumbing'ом (`git merge-tree`, `git read-tree`,
  `git commit-tree`) или `git stash` + обычный мерж в основном дереве.
  Урок 2026-10-24: три заведённых раньше дерева (`sotu-hud`,
  `sotu-work/icon-sheets`, осиротевший `sigil-concept-art` с мёртвым `.git`)
  разошлись с `main`, задублировали номера реестров (T-157 и D-226 — по два
  тикета/решения на номер) и сливались вручную, с ручным же перенумерованием
  занятых номеров.
- **Смена заканчивается запушенным `main`** (локальные коммиты без push = расхождение
  реестров, D-135).
- **Push-протокол (D-144 отменён D-224):** прямые коммиты в `main` — штатный режим; зелёный гейт обязателен **до push**, а не до коммита, потому что локальный коммит ничего не публикует. Отчёт без пуша помечается «локально, не запушено» (состояние — только git, D-138).
- **CI-поллинг агенту запрещён (директива владельца 2026-10-13):** агент НЕ опрашивает CI-2 — никаких `sleep 240/480`, `curl https://api.github.com/.../actions/runs`, парсинга `workflow_runs`, ожидания `success/completed` и merge-решений по статусам ранов. Pending/in_progress после push — не повод ждать: работу завершать, в отчёте писать «CI не проверялся (по инструкции)». Статусы CI — зона владельца; `game/report.sh`-блок под флагом `ENABLE_CI_WAIT` (по умолчанию `false`).
- Если мерж всё же возникает (наследная ветка, pull чужого pushа) — после резолва конфликтов **`git diff` против обоих родителей** (`HEAD^1`, `HEAD^2`) ДО коммита; `rerere` включён.
- Перед коммитом после мержа: `git grep -nE '^(<{7}|={7}|>{7})'` — вывод должен быть пуст (маркеры конфликтов, урок 67655e7).

- Сообщения коммитов — конкретные, по делу.
- **Номера D-* присваивает только реестр `docs/DECISIONS.md`**; коммиты/пуши номеров не получают.
- Пароли/токены не попадают в логи и коммиты.
