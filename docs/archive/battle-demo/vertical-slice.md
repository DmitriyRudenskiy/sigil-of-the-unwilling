# Vertical slice — полный цикл, вердикт по звеньям

Вопрос этого документа один: проходится ли цикл
**источник → кадр → аудит → спрайт → анимация → бой → UI** целиком, и где он
рвётся, если начать с чистого клона. Вердикт по каждому звену —
PROCEED / PIVOT / KILL. Дата: 2026-10-26.

Итоговый вердикт: **PROCEED с одним PIVOT и одним PIVOT-пометкой**.
Цикл проходится от начала до конца: бой доигрывает до победы в обоих наборах,
картинка в бою — генерированная, не заглушка. Ни одно звено не убито. Рвётся цикл
только при **повторении** с чистого клона: звено «источник» лежит вне репо.

## 1. Источник — PIVOT

`tools/spec.json` задаёт каталог источников абсолютным путём
`sources_dir = /Users/user/sigil-of-the-unwilling-slop/Новая папка с объектами 2`
и по каждой из десяти записей — имя файла источника. В git нет ни одного
источника (`assets/reference/` — один `walk-sample.png`), соответствие «файл →
id» ведёт `docs/asset-spec.md`.

Что это значит: с клона репо **нельзя** перегенерировать ни один кадр, не спросив
хозяина машины, где лежали исходные картинки. Соответствие источника id держится
таблицей, а не носителем (матрица, AC 52).

PIVOT, а не KILL: данные о соответствии есть, переносимы (десять файлов) и
стоят дешевле, чем риск их потерять. Что сделать: положить источники в
`assets/reference/` (или в репо-adjacent каталог, зафиксированный в `spec.json`
относительным путём) и добавить в `spec.json` проверку «источник существует».

## 2. Кадр — PROCEED, промежуточные носители теряются

Ветка, дошедшая до комплекта: A-pose первого кадра (`tools/gen_a_pose.py`,
`gen_a_pose_v2.py`, `assets/a_pose_v2/`) → edit по источнику и листу экипировки
(`tools/gen_kit.py`, `assets/kit/`) → DWPose-скелет (`tools/dwpose_cli.py`,
`make_poses.py`, `assets/poses/`) → I2V-клип (`tools/gen_clip_apose.py`,
`gen_clip.py`) → ункей и нарезка. Волк — отдельной звериной веткой
(`tools/gen_beast.py`). Покадровая ветка (`tools/gen_frames.py`, ADR-004/ADR-005)
осталась фолбэком.

Воспроизводимость генерации есть: `artifacts/generation-manifest.json` — 184
записи (путь, md5, seed, модель, промпт), `docs/generation-log.md` — реестр
прогонов с вердиктами, раннер возобновляемый (готовые кадры пропускаются,
`--reaudit` пересчитывает меру без генерации).

Минус: `assets/a_pose/` (18 файлов) и `assets/kit/` (44 файла) — **0 в git**
(оба в `.gitignore` с причиной «пересобираются»), `assets/poses/` — 224 из 413.
Промежуточный носитель звена теряется, и по AC 66 (лист экипировки) вердикт нечем
подтвердить из репо: ни отчёта, ни манифеста у кита нет — только картинка и
текст в `docs/`.

## 3. Аудит — PIVOT

Меры настоящие и строгие: `pivot_slide_x`, `pivot_sway_x`, `contact_slide_x`
(пороги 24 px / 8 px), `motion_first_last` (2.0), `chroma_share` (0.0005),
`flat_white_share` (0.25), `corner_before_clip` — пишутся в `report.json` каждого
клипа (`tools/gen_clip.py:360–376`). Именно `contact_slide_x` забраковал
`priest/hit` (65 px при пороге 8) — то есть мера работает и на отказ, а не только
на принятие.

Два расхождения с контрактом:

1. Мера считается **на входе генератора клипа**, поэтому отчёт есть по 23
   дорожкам из 45 (idle+walk девяти юнитов и пять дорожек волка). У дорожек,
   собранных раньше/другим путём, отчёта нет.
2. Названный в контракте фазы 7 пофайловый аудит (`tools/audit_sprites.py`:
   размер, альфа, число кадров, нейминг, дубликаты, отчёт со счётчиками) не
   написан. Приёмник существует — `tests/helpers/sprite_asserts.gd` (размер,
   альфа, пустой кадр, отсутствующий файл) и пять тестов на него, — но по
   комплекту из 196 файлов он не запускался.

PIVOT: инструмент почти готов, не хватает прогона по всему комплекту и отчёта.
Это же закрывает AC 40/44/46/50/61 и половину блокера 1 ворот.

## 4. Спрайт — PROCEED

`tools/build_sprite_frames.gd` (+ `.py`) собирает `*.sprite_frames.tres`: холст
128 px, силуэт 96 px, ступни в (64, 112) — то есть масштаб и pivot сводятся на
этом звене, а не оставляются на удачу. В git: 196 PNG + 10 `.tres`. Гейт
комплекта держит тест `test_sprite_tracks.gd` (пять дорожек по четыре кадра у
всех десяти юнитов, одна карантинная строка).

Расхождение с текстом спеки (512×512, `char_<side>_…`) — блокер 1 ворот, он про
форму кадра, не про проходимость звена.

## 5. Анимация — PROCEED

`scripts/view/battle_unit_view.gd`: `idle/walk/attack/hit/turn`, урон на
контактном кадре, гибель — последний кадр + обесцвечивание + крест, враг —
зеркало (`tools/mirror_anim.py`). Тесты: направление движения по стороне,
сохранение масштаба и pivot на развороте, остановка на последнем кадре гибели.
Дорожек `death` в данных нет ни у кого — требование «гибель без отдельной
анимации» выполняется конструктивно.

## 6. Бой — PROCEED

`scripts/combat/` — правила без единой ссылки на ноды и отображение
(`test_combat_without_scene.gd` проверяет и отсутствие `DisplayServer`-ссылок в
слое). 17/17 сценариев `turn-battle-core`: детерминизм по seed, очередь по
инициативе, одно действие за ход, статусы без стека, победа/поражение, ИИ
противника. Один и тот же бой двумя наборами — `test_roster_invariance.gd`.

## 7. UI — PROCEED

`scripts/view/`: поле, HUD, экран результата, выбор набора. 12/12 сценариев
`battle-demo-ui`, в том числе синхронность полос после **серии** действий и
игнорирование команд после результата. Визуальная приёмка — пять раундов
read-агента по живым кадрам, последний с md5 всех восьми кадров
(`docs/ui-read-judge-2026-10-26.md`).
