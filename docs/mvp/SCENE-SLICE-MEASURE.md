# Шаг 0 нарезки сцен: что измерено в комплекте

Отнесено к `openspec/changes/world-map-scene-slicing`,
решения **D-307** (номера тикетов), **D-309** (порог кластеров), **D-310** (вердикт по ролям,
даунскейлу и линиям) — реестр `docs/DECISIONS.md`. Вопрос, который это измерение
открыло, — **Q-M136** (`docs/QUESTIONS.md`). Числа ниже — доказательство, а не впечатление: они повторяются
командами из § «Как повторить» (D-192: вердикт, живущий в `/tmp`, не вердикт).

## Комплект (измерено, а не переписано из тикета)

| Факт | Значение |
| --- | --- |
| Файлов | 63 PNG, ни одного лишнего файла кроме PNG |
| Размеры | `1536×1024` — 43, `1470×1070` — 13, `1387×1134` — 4, ещё 3 редких |
| Предпосылка T-340 «1584×936» | **неверна** — ни одного кадра такого размера |
| Ориентация сетки на рисунке | pointy-top (вертикальные рёбра есть, градиенты пикуют на 0°/60/120°) |
| Период решётки | медиана 92 px по 22 кадрам из 63; разброс 52…136 px |
| Период против `GameNumbers.TILE_SIZE = 82` | медиана 1.12×; в полосе [82, 164] — 55% кадров |
| Кластеры палитры (k=2..8, k-means++, 60k пикселей) | локоть 3…5 (медиана 4); k для 85% дисперсии — 2…3 |
| Порог D-309 «к=6, кривая не просит большего» | **выполнен** — никто из 63 не просит больше пяти |

Даунскейл, который требовал зафиксировать D-310 (а), для этих кадров близок к 1:1
(период на рисунке ≈ 0.6…1.7 от 82 px), а не «18×», как ожидалось от 1584×936.
Смысл требования (один даунскейл, коэффициент в манифесте) не отменяется — меняется его
число.

## Что не работает (и это не «доделать метры»)

1. **Автопоиск решётки подгонкой не сходится.** Аффинная решётка `(W, начало)` объясняет
   0…22% нарисованных линий; вершина корреляции по кадру 0.28…0.59 при том, что на
   синтетике тот же код даёт 0.98 и остаток 1 px (самопроверка зелёная). Локальный период
   по девяти окнам одного кадра расходится на десятки пикселей — рисунок лежит на
   плоскости земли под перспективой, аффинное описание ему не принадлежит.
2. **Порог «здесь линия» не переносится между кадрами.** При пороге, общем для всего
   комплекта, штрихи находятся в 22 кадрах из 63; в остальных маска пустая или состоит из
   цветов и камней (они контрастнее линий сетки: `max(tophat, blackhat)` ловит и то и
   другое, а порог один на весь комплект). Попытка заменить её маской штрихов роняет
   покрытие даже на синтетике (0.98 → 0.31) — мере нужны свои пороги и свой прогон.
3. **Граница игровой зоны не отделяется.** По энергии отклика доля кадра p50 = 1.00
   (зона = весь кадр) при минимуме 0.52 — оправа достаточно «штриховая», чтобы порог её
   не отделил; корреляционный признак сработал как детектор зоны в 1 кадре из 63
   (`roi_source`: auto 1, field 62). Два независимых определения ориентации расходятся
   там, где штрихи вообще нашлись: подгонка даёт pointy 48 / flat 15, штрихи — 14 / 8.

Итог по шагу 0: **требование «клетки покрывают игровую зону без пропусков и наложений,
граница клетки отстоит от нарисованной линии не дальше N px» (AC1 спеки) этим комплектом
автоматически не выполняется** — ни одним из опробованных способов (корреляционная
подгонка, направление штрихов, спектр профиля, компоненты связности).

## Как повторить

```bash
python3 scripts/measure_scene_lattice.py --self-test      # синтетика: код годен
python3 scripts/measure_scene_lattice.py --all --geometry # период/ориентация по штрихам, 6 c
python3 scripts/measure_scene_lattice.py --all --update   # полная подгонка, ~7 мин
python3 scripts/measure_scene_clusters.py --self-test
python3 scripts/measure_scene_clusters.py --update        # k=2..8, игровая зона, палитра
```

Комплект — вне репозитория, путь в настройке машины (`MAP_SCENE_KIT` в
`~/.pi/agent/env/sotu-machine.env`, см. AGENTS.md § «Настройки машины»). Замеры сцен —
в `game/data/config/scene_slices.json` (реестр создаётся этими же скриптами).

## Дополнение 2026-11-08: вердикт «геометрия не восстанавливается» снят (D-311)

Владелец ответил на Q-M136 — (а) размечать кадры вручную. Разметка первой сцены
(`scripts/annotate_scenes.py`, игровая зона в реестр) показала, что отрицательный вердикт
выше был ложным: не хватало не чисел, а формы модели.

Три причины, по которым корреляция не видела сетку:

1. **Соты рисунка не равносторонние.** Шаг колодок 97…115 px при расстоянии
   центр-вершина 33…55 px (stretch C/(√3·R) = 1.09…1.75). Модель `W → h = W·2/√3`
   физически не могла совпасть с рисунком.
2. **Кадр под перспективой.** На первой сцене остаток решётки: 7.1 px медиана (24.6 p95)
   на голой решётке → 6.5 (15.9) при аффинной поправке → **1.11 px (2.61) при
   гомографии** на 83 полостях, 79 инлиеров. Аффинного преобразования мало.
3. **Маска.** Ридж-ответ (top-hat/black-hat × насыщенность) с одним порогом на 63 рисунка
   не переносился. Рабочая маска — «тёмное и малонасыщенное» с границей по Otsu самого
   кадра; линии дадут связные полости ячеек, и именно **полости** (соты) — правильный
   примитив: у них есть площадь, форма и центр, а у штриха нет ничего.

Новый носитель замера — `scripts/fit_scene_cells.py` (маска кадра → соты → шаг по
гистограмме соседних разностей → привязка в идеальной плоскости с RANSAC-гомографией →
остаток). Вердикт: **14 сцен из 63 сходятся автоматически** при остатке p95
0.77…3.98 px и покрытии сот 0.79…1.00; **26** не привязались к первично измеренному
шагу и **4** не дают читаемых сот — это очередь ручной разметки, а не «63 кадра».

Проверяемость: `python3 scripts/fit_scene_cells.py --self-test` (синтетика с
заведомой перспективой, 15% сот теряется, шаг возвращается в пределах 2 px, остаток
p95 1.48 px), кадр-доказательство совмещения — `tmp/cells-*.png` (красные соты поверх
рисунка; в git пиксели не идут, D-185).

Строки прогона выше (0 из 63, `line_coverage`, `peak`) остаются верной историей
корреляционного пути и больше не являются условием AC1.

## Дополнение 2026-11-08, вечер: профиль переиспользования (1.3–1.7)

Шаг 0 закрыт. Ноша — `scripts/measure_scene_clusters.py --cells` (режим того же
скрипта, что и профиль кадра: один инструмент на оба числа, потому что они читают один
`cell_fit`). Профиль пишется в реестр блоком `cell_profile`, политика — в корень реестра
блоком `policy`, и генерируется она из констант измерителя, а не переписывается прозой:
«удалить линии», «один проход ресемплинга» и «RMS в Lab» должны значить в нарезке ровно
то, что мерилось здесь.

### Что меряется (и почему именно так)

Клетка берётся не из кадра, а из **плоскости фитта**: кадр переносится обратной
гомографией сцены в прямую решётку, где клетка — прямоугольник `W × 2R`, и уже там
режется и приводится к 82×82 одним проходом. Резать в искажённом кадре нельзя: соседние
клетки наползали бы друг на друга, и переиспользование мерялось бы по чужим пикселям.

Сходство — RMS по Lab **только под маской гекса движка** (`gen_map_art.hex_mask`, D6):
углы квадрата клетки — это соседи, и без маски они утаскивают совпадения там, где их нет.
Кластеризация жадная по первому представителю, порядок обхода детерминирован: вопрос
«сколько тканей у сцены», а не «как разложить по k корзинам», поэтому k и случайные
старты здесь не нужны.

Удаление линий (Q-M135 → (б)) — маска тех же рёбер, что строит фитт, ремонт значением
ближайшего сохранившегося пикселя. `cv2.inpaint` не взят и не остался скрытым допущением:
диффузия при ширине разрыва 5 px затягивает клетку краской соседней, на синтетике с
четырьмя известными тканями это стоило трёх лишних кластеров из четырнадцати. Самопроверка
режима ловит ровно это: материал без сетки даёт четыре ткани, ремонт обязан вернуть
материал, а не подмешать новый.

### Числа (14 сцен с принятой геометрией, p50 по сценам)

| Порог D6 (RMS в Lab) | «тканей» на сцену | тайлов до 80% покрытия клеток | клеток без пары |
|---|---|---|---|
| 2 | 172 | 134 | 0.92 |
| 8 (порог спеки) | 90 | 56 | 0.46 |
| 16 | 34 | 6 | 0.10 |
| 32 | 3 | 2 | 0.00 |

Клеток на сцену p50 178. Базлайн «до удаления линий» — правая колонка той же таблицы,
170/98/42/4: **линии наивную меру не раздувают, а скрадывают разнообразие** (одинаковые
рёбра на каждой клетке делают разные ткани похожими). На пороге RMS 2 кадр с линиями
заявляет 4 ткани там, где их 10 — на этом примере проверка самопроверки и держится.

Порог 16 не принимается как порог тождества, и не из вредности: он шире собственного
цветового гейта проекта (ΔE ≤ 12, `map_art_gates.json`). Объявлять разное одной тканью
ради 80% покрытия значило бы нарушить §8.5, чтобы отчитаться по §8.9.

### Краска снята — переиспользования всё равно нет

Отдельное допущение, которое могло всё спасти: «клетки разные, потому что комплект
разнопаклён; сложите покраску — и останется общая ткань». Проверено так, как и просит
проверять: с каждой клетки снимается её собственная статистика поля (минус среднее, делить на
разброс — аффинная краска исчезает, светотень и зерно остаются). Шкала при этом обязана
смениться: после нормирования RMS двух *несвязанных* полей равен √2, поэтому прежний
порог «8» проходит сам собой; переведено в корреляцию полей, RMS² = 2(1−r).

| Корреляция полей рельефа r | «тканей» на сцену | тайлов до 80% покрытия | клеток без пары |
|---|---|---|---|
| ≥ 0.90 | 174 | 138 | 0.97 |
| ≥ 0.75 | 161 | 126 | 0.87 |
| ≥ 0.50 | 109 | 72 | 0.48 |
| ≥ 0.25 | 47 | 18 | 0.11 |

Вывод один: **уникален сам рельеф клетки, а не только её покраска.** Никакой слой
раскраски поверх переиспользуемого тайла этот разрыв не закрывает, потому что раскладывать
по полкам уже нечего. Проверка инвариантности (перекраска клетки не меняет ни одного
кластера нормированной меры и обязана менять D6-меру) не даёт этой норме врать.

### PSNR-потолок пути A (1.4) и палитра (1.5)

Тайл 82, возвращённый на нативный размер клетки: медиана по сцене p50 **36.2 дБ**,
минимум по сценам 31.0 дБ — требуемые 28 дБ не хуже. То есть путь A («по тайлу на
клетку») теряет не на качестве картинки, а на бюджете: 178 уникальных тайлов на сцену,
≈11 тысяч на комплект, и ни одна анимация поверх не ложится.

Палитра сот против полосы M (§8.5): в полосе (ΔE ≤ 12) p50 **8.5%** долей (минимум 0 —
есть сцены, где ни один доминирующий тон соты не попадает в полосу). После перекраски тем
же `recolor_cell`, которым генератор укладывает свою материю: p50 **87.6%**, минимум
68.2%. Расхождение действительно снимается существующим слоем (Q-M134 → (б)), и это единственная
из трёх надежд шага 0, которая подтвердилась.

### Вердикт шага 0 (1.7)

Ни один порог не делает из комплекта набор тайлов: AC1 («не менее 80% клеток из
ограниченного набора ≤ N при фиксированном пороге») выполняется только ценой порога,
нарушающего §8.5, либо ценой набора из 56…134 тайлов на сцену. Коэффициенты ресемплинга
при этом в норме: 0.71…0.85 по X и 0.75…1.23 по Y (единственная клетка 1.23 — единичный
фитт с перекосом; остальные в разумных пределах от 1:1). Диагностика политики
«удалить линии» тоже в реестре: доля пикселей зоны, сданных под линии, p50 14.7% при
максимуму 52.9% — на таком кадре маска ест террейн, и это видно числом, а не глазом.

Что делать с комплектом — **Q-M137**: (а) путь A как есть с бюджетом ~180 тайлов на
сцену, (б) комплект остаётся референсом, материю пишет генератор, (в) гибрид —
генерируемый террейн + одноразовые пропсы того, что и так уникально (дороги, строения,
границы), (г) ограничить носитель сценами с принятой геометрией. Агент без ответа
выбирает (в). Ручная разметка очереди (26 + 4 кадра) — труд **после** этого решения,
до него она может оказаться трудом в никуда.

## Дополнение 2026-11-09, вечер: профиль переиспользования и отклик на краску (1.3–1.7, D-312)

Измеряет `scripts/measure_scene_clusters.py --cells` (тот же скрипт, что `--fit-scene` и
`--recolor` — определения маски и меры должны быть одни для нарезки и для гейта).

```bash
GODOT=… python3 scripts/measure_scene_clusters.py --cells --cells-report=… --update
python3 scripts/measure_scene_clusters.py --self-test    # 16 проверок
```

Политика, которой меряет, записана **в корень реестра** блоком `policy`, сгенерированным из
констант скрипта: `line_removal` (маска замыкается, ядро `round(гипотенузы(масштаб ×
offset))` ≈ 3–5 px, ремонт одним проходом `inpaintRadius` ≤ толщине линии, до резки),
`resample` (единственное понижение, `SCALE_PRIORITY = [AREA, INTER_AREA, INTER_LINEAR]` —
никогда INTER_NEAREST; интерполяция **до** вычитания константы, иначе теряются нули),
`units` (дрейф — px p95, ткани — RMS на канале 0…255, покрытие — доля клеток). Смысл блока:
гейт и измеритель не могут разойтись в определениях, и расхождением нельзя отчитаться как
политикой.

| Мера | Единица | p50 (14 сцен) | Диапазон | Что значит |
| --- | --- | --- | --- | --- |
| Клеток в зоне | клеток/сцену | 178 | 125…232 | масштаб бюджета |
| Тканей при RMS 2 | тканей/сцену | 172 | 119…226 | клеток с дрейфом меньше порога нет |
| Покрытие 80% при RMS 2 | тайлов/сцену | 134 | 91…184 | путь A — это ≈11 тысяч тайлов на комплект |
| Тканей при RMS 8 | тканей/сцену | 90 | 61…148 | переиспользование начинается там, где клетка уже не клетка |
| Клеток без пары при RMS 8 | доля | 46% | 36…62% | формы расходятся шире любого порога тождества |
| Тканей после нормирования при r ≥ 0.9 | тканей/сцену | 174 | 121…228 | **уникален рельеф, а не покраска** |
| PSNR-потолок путей | дБ | 36.2 | 31.0…42.4 | путь A проходит по качеству (норма 28 дБ) и проваливается бюджетом |
| Доля сот в полосе M (референс палитры) | доля | 8.5% | 0…55% | соты живут вне своей палитры |
| …после `--recolor` (порог снят до 0.5) | доля | 87.6% | 68.2…99.8% | D-310 (б) снимает расхождение, дрейф клетки при этом не растёт |

Самопроверка дополнена четырьмя инвариантами: ковариация **до** интерполяции (один и тот же
хроматический узор при разных масштабах даёт отклик 0.98, после интерполяции — 0.34);
референс-палитра считается по **пикселям** полосы, а не по центроидам (иначе кластер из
двуглавой ячейки не попадает в палитру и меряет не то); покрытие 80% **не умеет выбирать
репрезентанта** (иначе одна и та же мера дважды даёт разные числа); ремонт линий обязан
держать остаток ниже толщины линии.

## Дополнение 2026-11-09: кадр как донор пропсов (шаг 3 после D-313, T-340)

D-313 оставил от нарезки одно: из сцен режется то, что уникально по своей природе и
генератором не производится. Проверить это можно только одним способом — попробовать
вырезать и посчитать. Носитель — режим `--props` того же скрипта: террейн отсекается по
**цвету** (доля самого частого hue-бина клетки ниже `palette.min_dominant_share` = 0.36 →
клетка не террейн; яркостный уход тона порог не двигает, иначе светотень становится
объектом), остаток связывается в компоненты, каждая привязывается к клетке фиттом D-311 и
попадает в блок `props` сцены с классом `object` / `road` / `patch` и рамкой.

```bash
python3 scripts/measure_scene_clusters.py --props --update
python3 scripts/measure_scene_clusters.py --props --scene=<кадр> --props-debug=tmp/props
```
