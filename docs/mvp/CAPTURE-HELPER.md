# Хелпер съёмки экрана

Инструмент визуальной приёмки «экран ↔ макет»: канонический размер кадра,
проверка этого размера, манифест снимка. Код — `game/tests/mcp/capture.py`,
точка запуска — `game/tests/mcp/test_capture.py`, захват — `game_screenshot`
через MCP (`GodotMCPClient.screenshot()` в `game/tests/mcp/godot_mcp.py`).

Нужен потому, что приёмка `T-147` (см. [[TICKETS]]) — это сравнение кадров
«до/после» и сверка с макетом, а молчаливое расхождение размера окна делало
такое сравнение недействительным без какого-либо сигнала.

## Почему размер нельзя было брать как есть

Замерено 2026-10-20 на живой сборке (Godot 4.7.2, экран 1920×1080):

| Способ | Кадр | Комментарий |
| --- | --- | --- |
| запуск по умолчанию | 1900×1007 | и так же 1818×1007 в прогоне приёмки `T-147` — **недетерминированно** |
| окно `size = (1920, 1080)` | 1920×1027 | зажато полезной областью; режим сам переключился в MAXIMIZED |
| `Window.MODE_FULLSCREEN` | **1920×1080** | размер верный, но **кадр заморожен** — см. правило 7; пин так не делается |
| окно без рамок: `borderless = true` + `size` | **1920×1080** | **нынешний пин**: те же пиксели, что у фуллскрина, и живой кадр |
| окно 1280×720 / 1024×768 | точно | достижимо всегда, но это не масштаб макета |
| Xvfb в `run_tests.sh` | 1024×768 | `Xvfb -screen 0 1024x768x24` — канон на гейт-хосте недостижим |

Отсюда два правила:

1. **Канон — 1920×1080** (`capture.CANONICAL_SIZE`): совпадает с
   `window/size/viewport_width|height` в `project.godot` и с макетами.
   Достижим окном **без рамок**: хелпер ставит `MODE_WINDOWED` + `borderless = true` +
   `size = канон` (без рамок строка меню не съедает 53 px). Полный экран даёт тот же
   размер, но на macOS замороженный кадр — см. правило 7; при каноне меньше экрана —
   явный размер окна.
2. **Расхождение размера = падение, не запись.** Фактический размер читается из
   IHDR готового PNG (`png_size`) и сверяется с каноном (`verify_frame`); при
   несовпадении — `CaptureError` с диагностикой (какой дисплей нужен, что
   поднимать на Xvfb, чем снять меньшим). Несравнимый кадр не попадает в
   приёмку молча.

Переопределение — `CAPTURE_SIZE=ШxВ` (например, для осознанной съёмки на
гейт-хосте). Канон при этом не «тихий»: он пишется в манифест каждого снимка.

## Команда воспроизведения

```sh
cd game
CAPTURE_SCENE=res://scenes/battle.tscn \
CAPTURE_LABEL=после CAPTURE_NAME=battle_after CAPTURE_OUT=battle-main-<sha> \
CAPTURE_SETUP=@/путь/к/setup_battle.gd \
GODOT_PATH=<бинарь Godot> \
GODOT_MCP_SERVER=$PWD/addons/godot-mcp/build/index.js \
python3 -m pytest tests/mcp/test_capture.py -q --timeout=900
```

`CAPTURE_SETUP` — необязательное **состояние** кадра: GDScript (инлайн или `@файл`),
который исполняется после пина окна и до съёма, одним `settle` на всё. Нужен там,
где кадр без кода пуст: `city_screen.tscn` автономно рисует каталог из одной
заглушки (`city == null`), и нулевая дельта такого кадра доказывала бы отсутствие
карточек, а не отсутствие сдвига. В манифест пишется sha256 исполненного кода, а
`CAPTURE_SETUP=…` добавляется в команду воспроизведения — кадр с состоянием
воспроизводится так же однозначно, как без него.

**Ловушка синтаксиса.** Раньше префикс `@` был обязателен: без него текст аргумента
считался инлайн-GDScript, путь до `res://` не компилировался, а симптом вёл не туда —
`MCPError: тулз game_eval вернул ошибку: eval failed: Failed to compile GDScript (error 43)`,
по которому ищешь ошибку в скрипте, а не в вызове (проверено 2026-10-25 на
`CAPTURE_SETUP=tools/capture/campaign_party_panel.gd`). С 2026-10-27 значение,
под которое существует файл (`tools/capture/<имя>.gd` или указанный путь), читается
как файл — `CAPTURE_SETUP=inventory_grid` и
`CAPTURE_SETUP=@tools/capture/inventory_grid.gd` дают один и тот же код; инлайн-
GDScript остаётся инлайном, пока файл с таким именем не найден.

**`CAPTURE_SCENE` — только путь `res://…`, и это проверяется.** Голое имя сцены
(`CAPTURE_SCENE=inventory_grid`) не роняло съёмку: `run_scene` не находил сцену,
в `current_scene` оставалась ПРЕДЫДУЩАЯ, и снимок сходился с ней байт в байт —
замер 2026-10-27: три «разных» кадра (меню, инвентарь, инвентарь с фикстурой) дали
один sha256 `965218a7…`, и все три были меню. Теперь `capture_scene` сверяет
`current_scene.scene_file_path` с заказанным путём и падает `CaptureError` до
съёма кадра.

Где кадр нужен вердикту, а не отладке, **файл сетапа коммитится** (D-192: пиксели git не
носят, а код, которым кадр поднят, обязан доживать вместе с вердиктом): пример —
`game/tools/capture/campaign_settings_open.gd` (поднимает `SettingsScreen` нажатием кнопки
кампанийного HUD, D-238). В таком коде нельзя называть имён блокируемых операций даже в
комментариях — песочница режет по исходнику (§10).

Без `CAPTURE_SCENE` тест съёмки помечен **skipped** — обычный гейт не тратит
живой Godot на инструмент, но и не молчит: в протоколе видна строка skip с
указанием на эту страницу. Логика хелпера (канон, IHDR, манифест, отказ при
расхождении) покрывается тестами без Godot и входит в обычный прогон.

## Чем снимать в разработке, чем — на гейте (2026-10-27)

Два канала, разные обязанности.

| Канал | Когда | Что доказывает |
| --- | --- | --- |
| `game/tools/shot_scene.gd` | шаг разработки: один кадр одной сцены | как выглядит правка прямо сейчас. В манифест не входит, канон 1920×1080 не доказывает: окно клампится (~1836×1025), инструмент пишет предупреждение и вердикт о размере не выносит |
| `tests/mcp/test_capture.py` + `CAPTURE_SETUP` | вердикт, приёмка, кадр в тред | канонический размер, IHDR, манифест, «сравнение валидно» |

Запуск съёмщика разработки — без MCP-сервера и без порта 9090, но НЕ headless
(dummy-рендер = отказ, а не чёрный кадр):

```bash
Godot --path game -s tools/shot_scene.gd -- \
  --scene=res://scenes/ui/artifact_inventory_screen.tscn \
  --state=inventory_grid --out=tmp/shots/inventory.png
```

`--state` — тот же файл из `game/tools/capture/`, что исполняет `CAPTURE_SETUP`
(имя без `.gd` либо путь), поэтому состояние под два канала не переписывается.
Отказы: `1` аргументы/сцена, `2` headless, `3` в дереве не та сцена, `4` кадр
чёрный (средняя яркость < 3), `5` фикстура не исполнилась. Относительный `--out`
считается от `game/`. Замер 2026-10-27: 429–437 мс на съёмку (окно + сцена +
фикстура + кадр), против 331 с на всю MCP-секцию.

## Манифест

`MANIFEST.md` в каталоге снимков, дописывается при каждом прогоне. Обязательные
поля: `HEAD` (полный sha), база (`origin/main`), дата/время (UTC), инструмент,
фикстура, канонический размер, команда воспроизведения, «сравнение валидно»,
оговорки; далее таблица файлов (состояние до/после, разрешение, байты, SHA-256).
Если прогон шёл с `CAPTURE_SETUP`, среди оговорок обязаны быть две строки: SHA-256 кода
состояния и его возврат (`CAPTURE_SETUP вернул: {…}`) — см. правило 7c.

## Где хранить

**PNG в репозиторий не кладём.** Причины: бинарные артефакты, пересоздаваемые,
раздувают историю, а политика хранения кадров ещё не решена. Файлы — в
`~/.local/share/sigil-reserve/<имя>/`; в тред ревью идёт **манифест текстом**
вместе с командой воспроизведения: ревьюер воспроизводит кадр сам, это сильнее
приложенной картинки. Картинку в тред можно приложить дополнительно, но не в git.

## Бутстрап свежего worktree

Хелпер запускается на живом Godot, а голое дерево к этому не готово:

1. `git worktree add <путь> -b <ветка> origin/main` — после `git fetch origin`.
2. `cd <путь>/game/addons/godot-mcp && npm ci && npm run build` — в свежем
   дереве нет `build/index.js` (~1 минута).
3. `godot --headless --path <путь>/game --import` — без кэша `.godot` живой
   Godot под MCP не поднимается: тесты валятся по таймауту `wait_ready` (~180 с),
   в логе сервера `No active Godot process`. Это признак непрогретого дерева, а
   не падения тестов.
4. **Первый `--import` на этой машине может сегфолить** (exit 139 на реимпорте
   шрифтов) — повторить; второй проход проходит чисто.
5. Дисплей обязан быть 1920×1080, иначе канон недостижим и хелпер упадёт с
   диагностикой (см. правило 2 выше).

## Гигиена дерева при съёмке

Два правила этого раздела — не про кадр, а про состояние дерева, в котором кадр
снимается. Оба куплены на подсрезе 2 города (`fix/t-147-city-shell`, 2026-10-20) и
оба умеют выдавать **правдоподобный зелёный**.

**A. Комментарий в `.tres` — только `;`, никогда `#`.**
Resource-формат Godot (`*.tres`, `*.res` текстовые) комментируется точкой с запятой.
Строка, начинающаяся с `#`, ломает разбор: в логе `Parse Error` →
`Condition "!int_resources.has(id)" is true` → `Failed loading resource` →
`Error loading custom project theme`, и тогда **тему теряет весь проект**, а не один
файл. Выглядит это как «экран перекрасился», а не как «экран сломался»: кадр остаётся
валидным по размеру и непустым, поэтому сравнение «до/после» его проглотит. Прецедент:
первый кадр «после» подсреза 2 — незакрашенный экран (56 КБ PNG против 100 КБ
закрашенного). Проверка: после любой правки `game/assets/theme/game_theme.tres` —
`godot --headless --path game --import` без `Error loading custom project theme` в
выводе; гард темы ловит поломку сам (`preload` носителя не проходит, файл падает на
discovery, код выхода 105), но это именно тот случай, где дешевле посмотреть в лог
до съёмки.

**B. `git checkout HEAD -- <файл>` откатывает и правки, сделанные после коммита.**
Контрольный кадр «до» требует вернуть затронутые файлы к состоянию `main`, и для этого
удобно откатиться через `HEAD`. Но `HEAD` — это последний **коммит**, а не состояние
минуту назад: незакоммиченная правка уезжает вместе с откатом. Прецедент: правка `#`→`;`
в теме была сделана в рабочем дереве после коммита, откат вернул битую версию, и
контрольный кадр «до» переснимался. Порядок, который это исключает: правка, меняющая
поведение, — сразу в коммит (или в `--amend`), и только потом откаты и сравнения.
Откатываться к `main` надёжнее явно: `git checkout origin/main -- <файл>`.

## Что считается обходом темы (T-147, уточнение 2026-10-20)

Правила ниже оперируют понятием «обход темы». По уточнению AC `T-147`
(прецедент `fix/t-147-tail`) **обходом темы считаются три механизма, а не один**:

1. `add_theme_*_override` в `.gd` — кодовое переопределение на узле;
2. `theme_override_styles/*` в `.tscn` — сценевое переопределение: оно побеждает
   тему ровно так же, как кодовое;
3. любой из двух **во вложенной сцене** — но принадлежность узла экрану
   определяется ответственностью, а не фактом попадания в дерево: `ArmyPanel` и
   `MinimapPanel/Frame` внутри `adventure_ui` — не проблема этого экрана, а
   следующий срез.

Отсюда **AC1 гарда формулируется по исходникам экрана (`.gd` + `.tscn`), а не
обходом дерева** (обход не отличает чужую сцену от своей и требует чужой работы
в чужом срезе). Объём `T-147` — **только стиль** (`add_theme_stylebox_override`
в коде + `theme_override_styles/*` в сценах, включая вложенные); `colors` /
`fonts` / `constants` вынесены в `T-148` (владелец, 2026-10-20).

## Что обязана доказывать приёмка экрана

Кадр и зелёный гард сами по себе ничего не доказывают. Ниже — десять правил,
каждое куплено на конкретном прецеденте (все — `T-147`, октябрь 2026): три про
кадр (AC2 — 1, 2, 5), два про гард (AC3 — 3, 6), два про валидность самого
сравнения и самого пикселя (4 — ушедшая база, 7 — зависший пин), два про то, где
гард слеп (8 — тип носителя, 9 — локализация дельты), одно про сам инструмент
съёмки (10 — песочница кода состояния).

**1. Кадр обязан быть непустым — это проверяется, а не предполагается.**
Панели, наполняемые из кода (`hero_status_panel`, `army_panel`, `info_panel`,
`adventure_ui`), нельзя снимать «как сцену»: кадр выходит валидным по размеру и
пустым по содержанию, а «ноль дельты» при пустом кадре тривиален. Обязателен
**контроль непустоты**: тот же кадр с выключенным носителем (скрытая сетка
секций, панель без героя) обязан дать **другой** хеш. Прецедент: витрина —
27 209 уникальных цветов против 2 129; мини-полосы — кадр без героя другой по
хешу, и только после этого ноль дельты что-то значит.

**2. К узлам, созданным кодом, идти по индексам, а не по имени.**
У такого узла имя вида `@GridContainer@4`, поэтому `find_child("GridContainer")`
возвращает `null`. Разыменование этой ссылки внутри `game_eval` **обрывает
соединение** `mcp_interaction_server`: в логе `Connection closed`, дальше
`No active Godot process` — выглядит как падение игры, но игрой не является
(тот же код в headless-ране печатает `SCRIPT ERROR` и живёт дальше). Путь —
`get_child(i)`-цепочкой; перед разыменованием проверять ссылку.

**3. Мутацию гарда проверять в дереве до запуска теста.**
Если патч мутации не применился (отступ, опечатка в имени), тест молча проходит
по чистому коду, а сила гарда оказывается переоцененной. Порядок: применить →
`git diff` / `grep` (мутация видна?) → запустить → `FAILED`. Прецедент: возврат
override'а на страницу вкладок в витрине сначала «не поймался» гардом — патч не
лёг по отступу; настоящая мутация дала `FAILED` в трёх срабатываниях.

**4. Кадр «до» на ушедшей базе валиден, если дельта баз не трогает игру.**
Если база сдвинулась между съёмкой «до» и «после», кадр не считается
недействительным автоматически: достаточно проверить, что
`git diff --name-only <база_до> <база_после>` не содержит файлов в `game/`.
Прецедент: «до» снято на `bb90bd30`, база ушла на `b2b66784` (OpenSpec-синк,
15 файлов, ноль в `game/`) — сравнение сохранено, гейт после ребейза переснят.
Если в дельте есть хоть один файл `game/` — переснимать обе половины.

**5. Технический перенос с нулевой дельтой доказывает не равенство кадров, а
переход власти — усиленный AC2.**
Равные кадры «до» и «после» доказывают только то, что пиксел не поехал. Экран при
этом мог остаться неуправляемым из темы: совпадающие кадры дают и настоящая
миграция, и перенос, после которого переопределение всё ещё сильнее носителя.
Поэтому к паре base-кадров обязателен **контроль чувствительности в обеих
половинах**:

- в «до» смена носителя на целевом узле **не обязана** менять кадр (и обычно не
  меняет: пока живо переопределение, вариант мёртв);
- в «после» смена носителя **обязана** менять кадр — это и есть доказательство,
  что тема получила власть, а не осталась за спиной узла;
- мёртвые узлы (стиля у типа нет или рисовать нечему) — **обратный контроль**:
  кадр не меняется ни до, ни после, и это заявлено в манифесте явно, иначе
  «не изменился» выглядит как незафиксированная слабость съёмки.

Прецедент: `fix/t-147-tail` — в «до» смена носителя на правой колонке,
слотах и кнопках инфо-панели кадр не меняла, в «после» меняет; мёртвый корень
диалога сундука не отреагировал ни там, ни там. Без этого контроля тикет был бы
выполнен по букве (grep = 0, кадр тот же) и не выполнен по сути.

**6. У каждого `assert_*` обязан быть терминал, а сила гарда доказана мутацией.**
`assert_bool(x)`, `assert_that(x)`, `assert_int(x)` в GdUnit4 только заворачивают
значение; проверка происходит в терминале (`is_true()`, `is_equal()`, `is_not_null()`…).
Цепочка `assert_bool(x).override_failure_message("…")` **полна синтаксически и пуста по
смыслу**: проверка есть в коде, её нет в прогоне, тест зелёный всегда. Отсюда — порядок
для любого нового гарда (подсрезы `T-147`, все будущие срезы темы и не только):

1. написать проверку с терминалом (`assert_bool(x).is_true()`);
2. прогнать — зелёный;
3. **сделать мутацию** (вернуть снятый override / сдвинуть перенесённое значение в теме);
   убедиться, что мутация легла в дерево (правило 3), и что прогон стал **красным**;
4. откатить мутацию, убедиться, что снова зелёный;
5. **протокол мутаций сохранить артефактом** — рядом с манифестом кадров (вне дерева):
   файл, значение до/после, текст `FAILED`. Мутации, сделанные и откатанные без записи,
   доказательством не считаются: их нельзя ни пересмотреть, ни повторить, и в отчёте они
   превращаются в строку «восемь мутаций покраснели». Прецедент: подсрез «армия»
   (`fix/t-147-army-artifact-tail`) — восемь мутаций заявлены прогнанными красным,
   артефакта не осталось, проверить это постфактум нельзя.

Зелёный прогон гарда не является доказательством, что гард что-то проверяет; доказательство —
красный прогон на намеренно сломанном, **и записанный**.

Прецеденты: **`T-123`** (2026-10-13) — 201 полупустой assert-сайт в 24 файлах, пять лет
зелёного свита, конверсия вскрыла латентные баги кода (off-by-one перерыва в
`SettlementResolve`, `>` вместо `>=` в дедлайнах квестов); **повтор 2026-10-20** —
`fix/t-147-city-chips`: первая версия гарда чипов города содержала три проверки без
терминала, мутация «фон чипа округлён до `Color(0.1882, …)`» (те же 48/255, другие биты)
прошла зелёным; и в тот же день тот же класс нашёлся в уже смерженном
`test_tail_screens_theme_carrier.gd` (7 проверок). Причина повтора: сканер
`scripts/ci2_vacuous_asserts.py` жил только в CI-2, а вердикт проекта — локальный прогон,
в который сканер не был подключён. Устранено веткой `fix/t-123-tail-guard-terminals`
(терминалы семи проверкам + `VACUOUS-ASSERT-GATE` в `game/run_tests.sh`, вызывается на
каждом локальном прогоне).
Черновик issue в gdUnit4 — [[GDUNIT4-VACUOUS-ASSERT-ISSUE]].

**7. Кадр обязан зависеть от состояния: пин окна — окном без рамок, а не полным экраном.**
Канонический размер 1920×1080 достигался переводом окна в `Window.MODE_FULLSCREEN`.
На macOS полноэкранное окно уходит в собственный Space, macOS перестаёт запрашивать кадры,
и `get_viewport().get_texture().get_image()` возвращает **первый** кадр после ухода в полный
экран. Хелпер молчал: снимок оставался побайтово верным по размеру и формату и **не менялся
ни от какого рантайм-состояния** — скрытый `CityScreen`, добавленный в дерево красный
`ColorRect`, смена носителя карточки. Ложью была и метрика живости: `Engine.get_frames_drawn()`
продолжал расти, поэтому «движок рисует» не опровергает залипания пикселей. Первые кадры
подреза каталога оказались побайтово равны пустому каталогу, и только сравнение с кадром
состояния это вскрыло.

Канон теперь собирается как `MODE_WINDOWED` + `borderless = true` + `size = target`
(рамки нет → строка меню не съедает 53 px, и 1920×1080 остаётся 1920×1080). Проверено:
(1) состояние меняет кадр, (2) два прогона равны, (3) кадр без состояния побайтово совпал
с каноническими кадрами, снятыми старим пином, — эквивалентность пина доказана, прежние
приёмки остаются в силе. Гард — `test_pin_window_code_не_уходит_в_полный_экран`.

**Общее правило для любого кадра состояния:** прежде чем сравнивать «до/после», убедиться,
что кадр меняется от заведомо видимого вмешательства в рантайм. Равенство двух кадров
доказывает дельту только тогда, когда известно, что эти кадры вообще что-то содержат.

**7a. Первый снимок после пина и смены состояния выбрасывается: отчётным должен быть
второй (T-188).** Симптом того же класса, что правило 7, но на Linux/Xvfb и без полного
экрана: `get_viewport().get_texture()` отдаёт **устаревшую** текстуру, если состояние
поменяло кадр только что. Замер (срез T-187): отчётный кадр хроники сошёлся побайтово с
кадром покоя (`92e8c588…` у обоих), при этом сразу после съёма тот же процесс отвечал,
что лента открыта, а следующий снимок подряд давал живой кадр (`f7075393…`). Воспроизвелось
на обеих попытках: первый снимок после пина+состояния (`11739a09…`) ≠ второй (`f7075393…`),
дальше кадры стабильны. Размер при этом канонический, сцена живая, состояние в дереве —
то есть молчание хелпера полное, а вердикт по такому кадру неверный и зелёный. У длинных
`CAPTURE_SETUP` (14 ходов кампейна в T-175) симптом маскировался: пока код крутился,
презентация успевала догнать.
Хелпер делает прайминг-снимок, ждёт `capture.PRIME_SETTLE_FRAMES` кадров и только следующий
снимок считает отчётным. Гард — `test_capture_scene_праймит_текстуру_до_отчётного_кадра`:
мок отдаёт разный рисунок на каждом снимке, и проверка видит, **чей именно кадр** ушёл в
SHA-256 манифеста. Тот же тест держит порядок: прайминг — после кода состояния, до отчётного.

**7b. Сетап кампейна обязан снять модалку первой директивы: иначе в кадре оверлей, а не экран
(T-189).** Оверлей T-186 — `CanvasLayer` со слоем 130 (выше HUD с 5) и открывается *отложенным*
запросом, то уже после `execute_code`. Коммитнутые сетапы, написанные до T-186, остались
зелёными и неверными одновременно: `campaign_settings_open.gd` поднимал экран настроек под
модалку «День 1», `campaign_chronicle_open.gd` — ленту хроники под неё же. При этом код экрана
работает, `is_settings_screen_open()` отвечает `true`, пиксели живые и меняются от состояния —
все признаки валидного кадра на месте, и вердикт по такому кадру читает не тот экран.
Снятие оверлея не «изменяет проверяемое состояние» — оверлей не часть проверяемого экрана:
в `CAPTURE_SETUP` после получения `hud` вызвать `hud.get_node_or_null("TutorialOverlay").dismiss()`
и `hud.bind_tutorial({})` (пустой список директив нужен потому, что запрос на показ приходит
позже: без него модалка вернулась бы следующим кадром). Проверено на обоих хелперах: до правки
в кадре модалка, после — форма настроек/лента.

**7c. Код состояния обязан отчитаться: кадр без отчёта — только пиксели (T-197).**
Симптом коварнее, чем 7a: хелпер не врёт — молчит о том, что состояние не применилось.
Замер (срез signs-prestige 2.3): кадр «плита Знака» сошёлся побайтово с кадром панели
отряда, снятым до этой правки (`0489bcaf…` у обоих), при живом коде плиты и свежеподнятом
Godot. Причина — не текстура и не прайминг: `set_sign`/`perform_sign_action` меняют
модель, а слой пересчитывается в `refresh_campaign`, который в игре вызывает хост. Сетап
поднял модель и ушёл, кадр остался состоянием «до».

Отсюда два правила. Первое: если носитель живёт на пересчёте слоя, `CAPTURE_SETUP`
обязан сделать этот пересчёт штатным путём хоста (`hud.refresh_campaign(day)`), а не
полагаться на то, что модель обновилась сама. Второе: хелпер пишет в манифест не только
SHA-256 кода состояния, но и то, что он вернул — строку `CAPTURE_SETUP вернул: {...}`.
Сетап, которому нечего вернуть о проверяемом состоянии, — кандидат на доработку: у
плиты это `plaque_visible`, `sign`, `rank`, `prestige` и `prestige_model` (число из
модели, чтобы манифест доказывал совпадение слоя с носителем, а не только наличие
текста). Гарды — `test_capture_scene_отдаёт_отчёт_кода_состояния` и
`test_capture_scene_без_кода_состояния_не_выдумывает_отчёт`. Совпавший с прежним кадром
другого экрана кадр — не «визуальное сходство», а красный флаг: состояние не применилось.

**8. Резолв из темы не доказывает, что носитель описан правильно.** Проверка
`node.get_theme_stylebox("panel")` сверяет **результат** поиска стиля, а не то, как
носитель объявлен. Если у фактического класса узла и у класса, указанного в `base_type`,
искомое имя стиля совпадает, движок резолвит стиль и при неверном `base_type`: у `Panel`
и `PanelContainer` рамка называется `panel` одинаково, поэтому носитель `MinimapFrame`
с `base_type = "PanelContainer"` отдаёт `Panel`-узлу ровно тот же ресурс, и гард на
резолв остаётся зелёным.

Это не «безвредная» правка, а мина замедленного действия: стоит следующему срезу
переименовать стиль, повесить носитель на узел другого класса или добавить стиль, у
которого имена расходятся, — и носитель поедет молча, без единого красного теста.
Отсюда требование к гардам переноса: **кроме проверки резолва гард обязан текстово
проверять декларацию носителя** — строку вида `MinimapFrame/base_type = "Panel"` в
файле темы (тема — ресурс, поэтому она читается `FileAccess` и сверяется строка).

Прецедент: `fix/t-147-minimap-carrier` (2026-10-21), мутация **M7** —
`MinimapFrame/base_type = "PanelContainer"` у носителя `Panel`-узла. Из девяти мутаций
протокола восемь покраснели, эта прошла **зелёным**, пока в гард не добавили текстовый
кейс на `base_type` (после — краснеет). Формула: **«резолв совпал» ≠ «носитель описан
правильно»**.

**9. Локализовать дельту по RGBA-разнице нельзя — `getbbox()` смотрит альфу.**
`ImageChops.difference(a, b).getbbox()` на RGBA возвращает `None`, когда отличаются
каналы RGB, а альфа одинакова (скриншоты Godot — RGBA, альфа везде 255). Замер
«где именно поехало» молча отвечает «нигде». Прецедент 2026-10-21
(`fix/t-147-artifact-carrier`): погрупповая раскраска узлов вернула четыре нуля,
включая заведомо живой `PanelContainer`, и контроль живости тоже ноль, хотя PNG на
диске различались в разы (10 594 байта против 197 544). Формула: «ноль дельты на
RGBA-разнице» ≠ «кадры равны».

Форма замера: сводить разность к поканальной маске максимума (`ImageChops.lighter`
по `split()`) либо считать в `L`/`RGB` до `getbbox()`. Побайтовое сравнение PNG
(`sha256`) остаётся безопасной мерой равенства; локализация — только по маске; и
любой ноль обязан сопровождаться контролем живости (правило 7), иначе он неотличим
от сломанного замера.

**10. Код состояния проходит песочницу `execute_code` — она блокирует по тексту.**
`CAPTURE_SETUP` исполняется внутри живого Godot через MCP-сервер, и тот отсекает
запрещённые операции **по исходнику кода**, а не по факту вызова: пока в тексте
встречается имя блокируемой операции (запись файлов), кадр падает с «Blocked
operation» — даже если имя стоит в комментарии и никакого вызова нет. `assert` в
этом же коде тоже не канал: он роняет interaction server, и прогон теряет кадр с
«Connection closed» вместо внятной ошибки. Прецедент 2026-10-21
(`fix/t-147-artifact-carrier`, бисект C/E5: три прогона подряд гибли на комментарии).

Практика: в `CAPTURE_SETUP` не писать имён блокируемых операций даже в
комментариях, не проверять им условия и не пытаться писать отчёт в файл — счётчики
и сверки выносить в headless-гард, а из кода состояния брать только само состояние.
Любой упавший кадр — бисектить по одной конструкции (файлом, не инлайном: инлайн
gd-код теряет табуляцию вместе с смыслом).

## Проверенное

- Два независимых прогона боя дают **один и тот же SHA-256** кадра
  (`8d20a48d…`, 1920×1080) — сравнимость «до/после» обеспечена.
- Недостижимый канон (`CAPTURE_SIZE=1920x1200`) даёт падение
  `кадр 1920×1027 ≠ канонический 1920×1200` с текстом диагностики.
- Пин «окном без рамок» даёт тот же кадр оболочки города, что прежний полноэкранный пин
  (`8c6a9a54…`), — смена пина не меняет пиксели, только честность снимка.
- Кадр состояния города (`CAPTURE_SETUP`) детерминирован: два независимых прогона —
  `841dcf99…`; чужой носитель карточек в этом состоянии меняет кадр (`0bbd19f2…`).
