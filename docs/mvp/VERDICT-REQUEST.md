## V-1. C-2 — Уровни города (campaign-city-level-progression)

- **Текущее состояние:** развитие поселения идёт через районы/здания/население
  (`district_system.gd`, `campaign_building_construction_service.gd`,
  `population_system.gd`). Отдельной шкалы «уровень города» в коде **нет**.
- **Вопрос:** нужен ли отдельный «уровень города» как прогрессия, или развития
  через районы/здания/население достаточно?
- **Варианты:**
  - (а) без отдельного уровня — развитие выражается районами/зданиями/населением;
  - (б) добавить «уровень города» как агрегат (пороги по построенному/населению).
- **Рекомендация (не финальная):** (а) — существующие системы уже покрывают
  развитие; отдельная шкала дублирует данные и добавляет верификацию.
- **Вердикт (владелец, 2026-10-20, D-216):** (а) — механических уровней города
  **нет**. Развитие через районы/здания/рабочих/население/престиж. `city_level`
  как механика не вводится; гейтинг зданий/районов/населения/действий уровнем —
  запрещён. UI-«ранг» — только косметическое производное. C-2 → **superseded**
  (баннер в main spec, прецедент C-9/D-215). Граница: новая прогрессия сверх
  районов/зданий/населения не создаётся. Legacy 52-hex city (`City.level`,
  world-режим) — вне кампанийного скоупа.
- **Блокирует:** `city-construction-districts` (building SM, district collapse,
  terrain adjacency), C-2-строка в `09-risks.md`.

## V-2. C-3 — Тактическая сетка боя (dnd-battle-ladder)

- **Текущее состояние:** бой = **абстрактная zone-ladder** (triumph/success/
  partial/failure/fumble) по margin-счёту (`campaign_battle.gd`), без
  тактической сетки/координат.
- **Вопрос:** достаточно ли абстрактной zone-ladder для MVP, или нужна
  тактическая сетка с координатами + Blink?
- **Варианты:**
  - (а) абстрактная zone-ladder (текущая, реализована и протестирована);
  - (б) тактическая сетка с координатами + способность Blink.
- **Рекомендация (не финальная):** (а) — zone-ladder закрывает MVP-бой
  (1v1 авто + авто-ИИ); сетка/координаты/Blink — Post-MVP.
- **Вердикт (владелец, 2026-10-20, D-217):** бой **без сетки и координат** —
  остаётся абстрактная лестница зон (позиция = зона, не клетка). `Blink` =
  переход между зонами (в разрешённую зону; без pathfinding/LOS/collision;
  обычная стоимость/кулдаун). Минимум: соседняя разрешённая зона / одна позиция
  по лестнице. Граница: сетка/тайлы/координаты/pathfinding/AoE-по-клеткам/
  визуальная тактическая карта — не добавляются.
- **Уточнение (владелец, 2026-10-20, D-222):** зональная реализация Blink
  **не одобрена** — позиционные зоны в боевом контракте не вводятся
  (ни `zone`-поле, ни 3-зонная лестница, ни переиспользование `terrain`).
  `Blink` в MVP **не реализуется** как механика; клеточные описания в доках
  переведены в статус «отложено вне MVP». Будущий безопасный дефолт (если
  Blink вернётся): 1/бой, без отдельной экономики действия, без модификаторов
  зон — только вместе с полноценной позиционной системой, отдельным вердиктом.
  **V-3 (босс) — без зон:** телеграфируемый удар по детерминированной цели.
- **Блокирует:** `dnd-battle-ladder` (C-3 координаты/Blink — теперь deferred,
  D-222), UI enemy card M1.

## V-3. F4 — Способности босса (vertical-slice / dnd-battle-ladder)

- **Текущее состояние:** бой с боссом идёт по ladder; **своих способностей**
  у босса нет (параметры TBD).
- **Вопрос:** какие **минимальные** способности босса для вертикального среза?
- **Варианты:**
  - (а) босс = сильный боец ladder без спец-способностей (только параметры);
  - (б) 1–2 спец-способности (напр., тяжёлый удар раз в N ходов).
- **Рекомендация (не финальная):** (а) для MVP-среза — босс как сильный боец;
  спец-способности — Post-MVP.
- **Вердикт (владелец, 2026-10-20, D-218):** минимальный набор — **ровно 2
  способности**, один упрощённый шаблон босса: (1) **телеграфируемый мощный
  удар** (по зоне, урон × 1.5, кулдаун 2 хода, цель — активная/ближайшая зона
  с живыми по логике лестницы); (2) **фаза ярости** (один раз при HP ≤ 50 %, +25 %
  к урону или эквивалент через существующие множители; без доп. фаз/призывов/
  контроля). Параметры — в данных (баланс без изменения кода). Граница:
  уникальные боссы, сложные фазы, миньоны, цепочки, спец-механики — до плейтеста.
  **Уточнение D-222:** зон нет — телеграфируемый удар по детерминированной цели.
- **Исполнено (2026-10-21, локальный агент):** `campaign_battle.gd` — `is_boss` +
  `_boss_strike` (мощный удар × 1.5, кулдаун 2 хода, детерминированная цель —
  штатный таргетинг) + `_check_boss_rage` (один раз при HP босса ≤ 50 % max,
  +25 % урона до конца боя); trace: `boss_powerful`/`boss_rage`. Данные:
  `campaign.json → raider_tier_3/raider_final` (`is_boss: true`, ×1.5/CD 2/≤50 %/
  ×1.25; урон 11 → 8 — компенсация, якоря T-041/T-041b зелёные). Не-боссы —
  штатный `_strike`. `test_battle_boss.gd` (9), GdUnit 2981/0. Spec «Enemy AI» и
  задача 2.2 синхронизированы с вердиктом.
- **Блокирует:** `dnd-battle-ladder` (F4 параметры босса), `vertical-slice`
  (босс финального рейда).

## V-4. Кривая occupation penalty (pregame-flow)

- **Текущее состояние:** `pregame_flow_model.gd:occupation_penalty(city_count,
  base=10)` — чистая value-функция, **base 10 = [PROPOSAL]**, механическое
  применение **отложено** (не подключено к геймплею).
- **Вопрос:** какая форма кривой (плоская/линейная/убывающая) и базовое
  значение штрафа за занятые города?
- **Варианты:**
  - (а) плоская: `base` за каждый занятый город (текущий [PROPOSAL], base 10);
  - (б) линейный рост с числом городов;
  - (в) убывающая отдача (шраф насыщается).
- **Рекомендация (не финальная):** (а) плоская base 10 — самая простая,
  согласуется с [PROPOSAL]; кривая тюнингуется в balance-слое.
- **Вердикт (владелец, 2026-10-20, D-219):** **мягкая линейно-ступенчатая кривая
  с капом**, без экспоненты и каскадной смерти. По времени под оккупацией:
  0 ходов → 0; 1–2 → −1; 3–4 → −2; 5+ → −3 (кап −3). Штраф — к городскому
  выходу/тренировке/существующим модификаторам (там, где уместно архитектурой).
  После освобождения −1 за каждый полный ход до 0. Детерминированно, без
  случайных штрафов. Граница: дипломатия/восстания/потерянные здания/перманентные
  дебаффы — без отдельного решения. Заменяет [PROPOSAL] плоский base 10.
- **Блокирует:** `pregame-flow` (механическое применение occupation penalty),
  pregame-flow 2.x.

## V-5. REST — персистентный HP между боями (party-characters 2.2)

- **Текущее состояние:** бой 1v1 авто по ladder; **персистентного HP между
  боями нет** (WOUNDED/UNSTABLE — внутри боя, T-116; потери между боями = DEAD,
  реализовано).
- **Вопрос:** нужен ли персистентный HP между боями (механика REST/отдыха) для
  MVP?
- **Варианты:**
  - (а) без персистентного HP — между боями полное восстановление, потери = DEAD;
  - (б) персистентный HP + REST (восстановление за ресурс/время).
- **Рекомендация (не финальная):** (а) для MVP — без персистентного HP
  (потери уже реализованы как DEAD); REST — Post-MVP.
- **Вердикт (владелец, 2026-10-20, D-220):** **ввести упрощённый персистентный
  HP** (взято (б), не рекомендация). `current_hp` сохраняется между боями; бой
  стартует с текущим `current_hp`. REST в городе полностью восстанавливает HP
  живым + снимает излечимые негативные состояния (WOUNDED/UNSTABLE). Мёртвые не
  восстанавливаются. Бой на 0 HP с выживанием по death saves → после боя 1 HP +
  ближайшее состояние ранения. Граница: временные хиты, short rest, сложное
  лечение, болезни, долгосрочные травмы — не вводят.
- **Исполнено (2026-10-21, локальный агент; план-гейт подтверждён владельцем,
  D1–D4):** `party_system.gd` — `ensure_hp` (идемпотентная миграция: без
  `current_hp` → полный; ≤0 → 1+WOUNDED; DEAD не воскрешаем), `rest` (живые
  READY/WOUNDED → max_hp/READY; DEAD не трогаем), `apply_battle_result` (dead →
  DEAD/0; hp>0 → keep; hp≤0 → 1+WOUNDED), `hero_max_hp` (warrior-статблок,
  фолбэк 45). **D1:** герой боя = первый живой член ростера; `character_uid` —
  uid самого героя (либо −1: только-ростерный член, потерь населению нет,
  двойной смерти нет). **D2:** `max_hp` всех членов = warrior-прокси (класс-
  маппинг — вне V-5). **D3:** REST автоматически в settlement-фазе при герое в
  городе (шов: поход → REST нет → урон переносится). **D4:** `WOUNDED` —
  ростерный статус без штрафа (живой: alive_members/wipe/лимит; снимается
  REST'ом). Миграция: `init_campaign` + `load_save_state` + новый член
  (training). Смерть героя → ровно один DEAD; wipe-проверка — в write-back
  (uid −1 обходит losses). Адаптировано 2 теста (старые формулы
  «герой не член партии» / «WOUNDED не переносится» аннулированы V-5).
  `test_party_hp_rest.gd` (+15), GdUnit 3010/0, 0 orphans; якоря T-041/T-041b
  зелёные (REST каждый ход → старт боя с полным HP, как до V-5).
- **Блокирует:** `party-characters` 2.2 (REST) — снято.

## V-6. Training: total vs alive (party-training)

- **Текущее состояние:** **несогласованность** —
  `campaign_training_service.gd:88` гейтит тренировку по **ВЕСЬ**
  `party.size()` (включая DEAD), а `party_screen_model.gd` / settlement-
  потребление считают **alive** (`alive_members`). При 5 членах, из которых 3
  мёртвы, тренировка заблокирована, хотя по alive-модели слот свободен.
- **Вопрос:** гейтить ли тренировку по **alive-модели** (живых < capacity) или
  по **total-составу** (включая DEAD)?
- **Варианты:**
  - (а) alive-модель — согласовано с экраном партии и settlement (оба считают alive);
  - (б) total (текущее в `campaign_training_service.gd`).
- **Рекомендация (не финальная):** (а) alive-модель — устраняет несогласованность
  и соответствует канон-намерению подсказки «слот освободится смертью».
- **Вердикт (владелец, 2026-10-20, D-221):** **alive-модель** (взято (а)).
  Тренировка/рекрутинг/замена мёртвых/лимит партии — только ЖИВЫЕ: активный
  лимит ≤ 5 живых; DEAD не занимают слот и не блокируют; DEAD остаются в
  истории/ростере, но не в capacity; рекрут занимает живой слот при
  alive_count < capacity. Чинит `campaign_training_service.gd:88` (total) →
  alive. Граница: вся модель ростера не переделывается — только гейтинг + тесты.
- **Блокирует:** `party-training` (гейт), консистентность подсказки 3.2 на
  экране партии.
