# VERDICT-REQUEST — решения владельца, блокирующие работу агента

Документ-сводка для владельца: 6 вердиктов, которые блокируют завершение
агентских OpenSpec-изменений. По каждому: **текущее состояние** (что уже в
коде), **вопрос**, **варианты**, **рекомендация (НЕ финальная — право решения
за владельцем)** и **что блокирует**. Агент **не реализует** блокируемые
механики до вердикта; рекомендации — точка входа для обсуждения, не канон.

Статус документа: `reference`. После вердикта владельца каждая строка
закрывается записью в `DECISIONS.md` (номер D-*) + синхронизацией
соответствующего change.

## V-1. C-2 — Уровни города (campaign-city-level-progression)

- **Текущее состояние:** развитие поселения идёт через районы/здания/население
  (`district_system.gd`, `campaign_building_construction_service.gd`,
  `population_system.gd`). Отдельной шкалы «уровень города» в коде **нет**.
- **Вопрос:** нужен ли отдельный «уровень города» как прогрессия, или развития
  через районы/здания/население достаточно?
- **Варианты:**
  - (а) без отдельного уровня — развитие выражается районами/зданиями/населением;
  - (б) добавить «уровень города» как агрегат (пороги по построенному/населению).
- **Рекомендация (не финальная):** (а) — существующие системы уже покрывают
  развитие; отдельная шкала дублирует данные и добавляет верификацию.
- **Блокирует:** `city-construction-districts` (building SM, district collapse,
  terrain adjacency), C-2-строка в `09-risks.md`.

## V-2. C-3 — Тактическая сетка боя (dnd-battle-ladder)

- **Текущее состояние:** бой = **абстрактная zone-ladder** (triumph/success/
  partial/failure/fumble) по margin-счёту (`campaign_battle.gd`), без
  тактической сетки/координат.
- **Вопрос:** достаточно ли абстрактной zone-ladder для MVP, или нужна
  тактическая сетка с координатами + Blink?
- **Варианты:**
  - (а) абстрактная zone-ladder (текущая, реализована и протестирована);
  - (б) тактическая сетка с координатами + способность Blink.
- **Рекомендация (не финальная):** (а) — zone-ladder закрывает MVP-бой
  (1v1 авто + авто-ИИ); сетка/координаты/Blink — Post-MVP.
- **Блокирует:** `dnd-battle-ladder` (C-3 координаты/Blink), UI enemy card M1.

## V-3. F4 — Способности босса (vertical-slice / dnd-battle-ladder)

- **Текущее состояние:** бой с боссом идёт по ladder; **своих способностей**
  у босса нет (параметры TBD).
- **Вопрос:** какие **минимальные** способности босса для вертикального среза?
- **Варианты:**
  - (а) босс = сильный боец ladder без спец-способностей (только параметры);
  - (б) 1–2 спец-способности (напр., тяжёлый удар раз в N ходов).
- **Рекомендация (не финальная):** (а) для MVP-среза — босс как сильный боец;
  спец-способности — Post-MVP.
- **Блокирует:** `dnd-battle-ladder` (F4 параметры босса), `vertical-slice`
  (босс финального рейда).

## V-4. Кривая occupation penalty (pregame-flow)

- **Текущее состояние:** `pregame_flow_model.gd:occupation_penalty(city_count,
  base=10)` — чистая value-функция, **base 10 = [PROPOSAL]**, механическое
  применение **отложено** (не подключено к геймплею).
- **Вопрос:** какая форма кривой (плоская/линейная/убывающая) и базовое
  значение штрафа за занятые города?
- **Варианты:**
  - (а) плоская: `base` за каждый занятый город (текущий [PROPOSAL], base 10);
  - (б) линейный рост с числом городов;
  - (в) убывающая отдача (шраф насыщается).
- **Рекомендация (не финальная):** (а) плоская base 10 — самая простая,
  согласуется с [PROPOSAL]; кривая тюнингуется в balance-слое.
- **Блокирует:** `pregame-flow` (механическое применение occupation penalty),
  pregame-flow 2.x.

## V-5. REST — персистентный HP между боями (party-characters 2.2)

- **Текущее состояние:** бой 1v1 авто по ladder; **персистентного HP между
  боями нет** (WOUNDED/UNSTABLE — внутри боя, T-116; потери между боями = DEAD,
  реализовано).
- **Вопрос:** нужен ли персистентный HP между боями (механика REST/отдыха) для
  MVP?
- **Варианты:**
  - (а) без персистентного HP — между боями полное восстановление, потери = DEAD;
  - (б) персистентный HP + REST (восстановление за ресурс/время).
- **Рекомендация (не финальная):** (а) для MVP — без персистентного HP
  (потери уже реализованы как DEAD); REST — Post-MVP.
- **Блокирует:** `party-characters` 2.2 (REST).

## V-6. Training: total vs alive (party-training)

- **Текущее состояние:** **несогласованность** —
  `campaign_training_service.gd:88` гейтит тренировку по **ВЕСЬ**
  `party.size()` (включая DEAD), а `party_screen_model.gd` / settlement-
  потребление считают **alive** (`alive_members`). При 5 членах, из которых 3
  мёртвы, тренировка заблокирована, хотя по alive-модели слот свободен.
- **Вопрос:** гейтить ли тренировку по **alive-модели** (живых < capacity) или
  по **total-составу** (включая DEAD)?
- **Варианты:**
  - (а) alive-модель — согласовано с экраном партии и settlement (оба считают alive);
  - (б) total (текущее в `campaign_training_service.gd`).
- **Рекомендация (не финальная):** (а) alive-модель — устраняет несогласованность
  и соответствует канон-намерению подсказки «слот освободится смертью».
- **Блокирует:** `party-training` (гейт), консистентность подсказки 3.2 на
  экране партии.
