# Design: quests-reputation-system

## Context

- Герой: `HeroController` + компоненты. `HeroStatsComponent` хранит
  `hero_race`, `hero_class` (заполняются из `HeroBuildProfile` в
  `apply_build`) и `serialize()`/`deserialize()` — единая точка сейва героя.
- Раса/класс: `HeroRaces.RACES` (6 рас: human, elf, dwarf, aumaua, orlan,
  godlike), `HeroClasses.CLASSES` (12 классов, включая priest/paladin).
- Городская репутация уже существует — `scripts/city/ReputationSystem.gd`
  (репутация города с населением, −100..+100, банды REBELLION..GOLDEN_AGE).
  Это **другая** система: новая фракционная репутация названа
  `FactionReputation` во избежание конфликта class_name.
- Квестов в проекте не было: ни данных, ни системы, ни UI.
- Паттерны кодовой базы: статические системы-калькуляторы
  (`LeadershipCheck`, `DeceptionCheck`, `ExtractRules`), данные в
  `scripts/data/*.gd` с `const`-таблицами, GdUnit4-тесты в
  `tests/unit/systems/`.

## Goals / Non-Goals

**Goals:**
- 6 фракций 1:1 по расам; репутация −100..+100, 5 уровней
  (Враг/Недруг/Нейтрал/Друг/Союзник).
- Модификаторы: цены ×0.8..×1.5, найм с уровня Друг (+10).
- 4 типа процедурных квестов (kill/gather/deliver/escort), сложность по
  кольцу 1–3, награды xp/gold/reputation.
- Прогресс, провалы (таймер −10, гибель NPC эскорта −20), цепочки
  (`next_quest_id`), журнал.
- Состояние квестов и репутации переживает сейв.

**Non-Goals:**
- NPC-юниты эскорта на карте (реализован только провал по смерти).
- Трекинг цели квеста на карте и компас.
- Агрессивные патрули фракции при уровне "Враг".
- Триггер "визит в город впервые за N ходов" — генерация вызывается
  явным вызовом `QuestSystem.generate_quests(state, faction, ring, rng)`.
- Диалоги, сюжетные квесты с катсценами, мультиплеер.

## Decisions

### D1: Статические системы с явным state (Dictionary), не autoload

`FactionReputation` и `QuestSystem` — `RefCounted` со статическими
функциями, state принимается/возвращается как `Dictionary`. Как
`LeadershipCheck`/`ExtractRules`.

- **Почему:** детерминизм тестов (state — plain data, нет скрытых
  глобалов), лёгкая сериализация (JSON-ready), нет конфликта с autoload.
- **Альтернатива:** autoload-синглтоны — отклонено: глобальное мутабельное
  состояние усложняет тесты и сейвы.

### D2: Фракции 1:1 по id расы

`HeroFactions.FACTIONS` keyed по `hero_race`. Родная раса — бонус
+10 к начальной репутации и ×1.1 к положительным дельтам своей фракции.

- **Почему:** spec требует 6 фракций "по числу рас"; совпадение id
  убирает отдельную таблицу соответствия.
- Классовый бонус: priest/paladin +5 к `godlike` (Храм Высших).

### D3: Награды по кольцу, репутация — среднее

`RING_REWARDS`: кольцо 1 → {xp 20, gold 15, rep 10}, 2 → {50, 40, 20},
3 → {120, 100, 30}. Spec даёт диапазоны (+10..+30) — взято среднее
значение диапазона, не хардкод по квесту.

- **Почему:** одна таблица, детерминированно, достаточно для MVP.
  Уточнение по типу квеста — upgrade path.

### D4: Провал — только два события

`fail_quest(state, id, reason)`: `timeout` (−10) и `escort_dead` (−20).
Таймеры проверяются `check_deadlines(state, day)` — вызывается раз в день.

- **Почему:** spec называет именно эти два события провала. Остальные
  причины (например, смерть героя) не описаны — не добавляем.

### D5: Сейв через HeroStatsComponent

`quest_state`, `faction_rep`, `rep_history` — поля компонента, попадают в
`serialize()` автоматически (HeroController.serialize шьёт все компоненты).
Начальное состояние — в `apply_build` (после установки race/class):
`FactionReputation.initial_state(race, class)` и `QuestSystem.new_state()`.

- **Почему:** не трогать `WorldPersistence`/`SaveData` — герой уже
  сериализуется целиком, новые ключи backward-compatible
  (`data.get(key, default)`).
- **Альтернатива:** отдельные поля в SaveData — отклонено: больше файлов,
  та же надёжность.

### D6: Программный UI без .tscn

`QuestJournalScreen` и `FactionScreen` — `CanvasLayer`, строят дерево
нод в `_init()` (как большинство панелей проекта). Журнал: 3 таба
(активные/завершённые/проваленные) + кнопка "Сдать" при
`progress >= target_count` (сигнал `quest_turned_in`). Экран фракций:
6 строк (название, значение, уровень, цены, найм) + история (RichTextLabel).

- **Почему:** headless-безопасно (не нужно .tscn для тестов), минимум
  файлов.
- **Альтернатива:** .tscn-сцены — отклонено: не даёт выигрыша,
  усложняет headless-прогоны.

### D7: Типизация GDScript 4 — явные типы из Variant

`var target_count: int = int(RING_TARGET_COUNT[ring])` — константные
Dictionary возвращают Variant, `:=` не инферится. `static const` в
GDScript 4 не валидно — `const`.

## Risks / Trade-offs

- **Генерация квестов не привязана к миру** (нет триггера визита в
  город): квесты появятся только когда UI/игровой цикл начнёт вызывать
  `generate_quests`. Риск принят — интеграция с миром отдельной задачей.
- **Эскорт без NPC на карте**: провал `escort_dead` вызывается внешним
  кодом, когда NPC умрёт. До реализации NPC-эскорта квест эскорта
  завершается ручным `add_progress`.
- **Репутация не влияет на торговлю пока**: `price_multiplier` доступен,
  но MarketSystem не подключён. Точка интеграции:
  `MarketSystem` × `FactionReputation.price_multiplier`.
- **6 фракций = 6 рас**: если добавится 7-я раса — нужна 7-я фракция
  (таблица `HeroFactions.FACTIONS` расширяется, код не меняется).

## Migration Plan

Новая фича, миграции нет. Старые сейвы: `data.get("quest_state", {})` →
пустое состояние; `apply_build` не вызывается повторно при загрузке,
поэтому старый герой получит начальную репутацию при следующем
создании/пересоздании профиля. При загрузке сейва с пустым
`faction_rep` — все фракции 0 (Нейтрал), что допустимо.

## Open Questions

- Подключить ли `price_multiplier` к `MarketSystem` сейчас или в
  отдельном change (рекомендация: отдельный, чтобы не раздувать).
- Нужен ли триггер генерации квестов для MCP-тестов (детерминированная
  генерация уже покрыта unit-тестами с фиксированным seed).
