## Context

`game/` — это Godot-проект (root = `game/`, `res://` → `game/`). В `game/assets/` ~800 файлов: `units/` (384), `artifacts/` (108), `cursors/` (64), `ui/icons`, `ui/hero`, `textures`, `tiles`, `audio`, `raw`. Референсы делятся на две категории:

- **Статические** — literal `res://assets/...` в `.gd`/`.tscn`/`.tres`/`.json` (аудио, иконки, тайлы, `ui/*`, `raw/*`).
- **Динамические** — строятся через `%` из ключей данных: `UnitSprites.gd` → `"res://assets/units/%s.png" % key` и `"%s_s.png"`; `ArtifactInventoryScreen.gd` → иконки статов по `art.id`. Файл «используется», если ключ есть в игровых данных; при отсутствии ключа работает фолбэком (`swordsmen.png`).

Существует верификационный runner `game/tools/shell/run_operability.sh` (сцены/сценарии/юнит-тесты, вердикты CLEAN/DIRTY) и `docs/CONSOLE_ALLOWLIST.md`. Их нужно переиспользовать, а не дублировать.

## Goals / Non-Goals

**Goals:**
- Дать повторяемый, неопасный способ найти неиспользуемые ассеты и переместить их в `_archive`.
- Обеспечить мгновенный откат через `manifest.json` + git.
- Подтвердить, что после архивации игра остаётся `CLEAN`.

**Non-Goals:**
- Ручной перебор файлов человеком (это и есть проблема).
- Изменение игрового кода/данных (только чтение как источники референсов).
- Определение «ценности» ассета (дизайн/бизнес) — только факт использования.
- Чистка несвязанных с ассетами мусорных файлов (`.DS_Store`, `.import` вне `assets/`).

## Decisions

**D1. Standalone Python-анализатор, а не Godot-тул.**
Статический анализ путей не требует запуска Godot (стартап ~сек/запуск, а проверок много). Python 3 уже есть на macOS, без внешних пакетов. Это ближе к конвенции shell-тулов (`check_console_clean.sh`, `play_scenario.sh`).
*Альтернатива*: Godot-тул (`-s analyze_assets.gd`) — в стиле `compile_all.gd`, но медленнее и сложнее парсить `%`-формат и данные.

**D2. Алгоритм детекции: used-set = static ∪ data-driven.**
- Enumerate все файлы под `game/assets/` кроме `*.import`.
- Static: regex `res://assets/<path>\.(ext)` по `.gd/.tscn/.tres/.json` → добавляем в used.
- Data-driven: в `.gd` ищем шаблоны `"res://assets/units/%s..."` и иконки, извлекаем место вставки `%s`, затем резолвим его против вселенной ключей (D3).
- Unused = files − used. Детерминировано (сортировка, фиксированным порядок обхода).

**D3. Universe-of-keys (data-aware) — источник «реальных» ключей.**
Динамический путь считается использованным только если его ключ есть в данных. Нужно локализовать, где определены юниты/артефакты/иконы (из `UnitSprites` ключ `key` приходит из runtime-данных). В реализации — найти определение (json/dict в скриптах) и извлечь все ключи. Это единственное место, требующее изучения кода в процессе реализации; спецификация поведение не меняет (требование к детектору — «знать вселенную ключей»).

**D4. Положение `_archive` — корневая папка репозитория (вне `game/`).**
Перемещение за пределы `game/` полностью вынимает ассеты из `res://` (Godot перестаёт их импортировать/грузить) — это истинный «архив». Откат: вернуть файл по fs-пути из manifest + `git`.
*Альтернатива*: `game/assets/_archive/` — остаётся внутри проекта (Godot всё равно импортирует, но без runtime-референса безвредно); проще по путям, но не убирает асеты из active tree. Выбор — дефолт, легко поменять (D6/Open Questions).

**D5. Manifest как единственный механизм отката.**
`manifest.json` (в `_archive/`): массив `{ res_path, fs_path, dest_path, category, reason }`. Перемещение всегда с `.import`-сайдкаром. Без manifest — архивация не считается завершённой.

**D6. Верификация через существующий runner.**
После архивации — `game/tools/shell/run_operability.sh`. Вердикт `CLEAN` → принять; `DIRTY` → откат из manifest + отклонение.

**D7. Режимы CLI: `report` (dry-run, по умолчанию) и `archive`.**
`report` никогда не пишет/перемещает. `archive` — только по явному флагу. Это гейт от случайного удаления (D0 из proposal: ambiguous → keep).

## Risks / Trade-offs

- **[D3] Не найдём/неверно извлечём вселенную ключей → ложный unused.** → Митигация: `report` показывает кандидаты; архивация только после ручного ревью списка в `report`; верификация `run_operability.sh` ловит промах (DIRTY → откат).
- **[D4] Асеты уходят из `game/` → нужно пересчитать относительные пути в manifest/откате.** → Митигация: храним абсолютные fs-пути; откат — копирование по fs, не через Godot.
- **[D2] Динамические пути, которых нет в текущем коде (будущие ключи).** → Митигация: правим детектор при добавлении новых типов ассетов; ambiguous → keep.
- **[D5] Manifest потеряется → безоткатный архив.** → Митигация: manifest в том же `_archive/` + git-история отслеживает перемещения.

## Migration Plan

1. `report` — сгенерировать список кандидатов, ручное ревью.
2. При согласии — `archive` → перемещение в `_archive/` + запись `manifest.json`.
3. `run_operability.sh` → должен быть `CLEAN`.
4. При `DIRTY` → откат из manifest, исправление детектора, повтор.
5. Запись процесса в `docs/` (без дублирования `run_operability.sh`/`CONSOLE_ALLOWLIST.md` — только ссылка на них).

## Open Questions

- **D4-альтернатива**: `_archive` в корне репозитория vs `game/assets/_archive/` — подтвердить дефолт (корень).
- **Источник ключей (D3)**: где именно определены юниты/артефакты/иконы (json vs dict в скриптах) — уточнить в реализации.
- **Охват `raw/`**: некоторые `raw/*` могут быть «сырыми» исходниками, которые не используются напрямую, но могут понадобиться — включать в архивацию по общему правилу или выносить отдельно? (по умолчанию — по общему правилу unused.)
