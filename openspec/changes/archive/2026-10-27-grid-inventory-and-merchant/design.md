## Context

Снаряжение героя (см. proposal.md — Why):

- `HeroInventory` (`game/scripts/entities/hero_inventory.gd`) — `equipped: Dictionary`
  по слотам `Artifact.Slot` и `backpack: Array[Artifact]` с лимитом «по количеству»
  (`MAX_BACKPACK_SIZE = 16`, `game_numbers_hero.gd:7`). `add_to_backpack()` проверяет
  только длину массива и дубль id; `sell_artifact()` возвращает `value_gold * 0.5`
  и **не вызывается никем**.
- Экран `ArtifactInventoryScreen` собирается генератором
  `scripts/build/gen_inventory_scene.gd` в `scenes/ui/artifact_inventory_screen.tscn`
  и листает рюкзак по 6 ячеек (`BackpackSlot_%d`, `_refresh_backpack()`), иконку
  резолвит `assets/artifacts/%s.png`.
- `Artifact` уже моделирует почти всё из брифа: `DamageType`
  (SLASHING/PIERCING/BLUDGEONING), `crit_threat`/`crit_multiplier`,
  `WeaponCategory` (SIMPLE/MARTIAL/EXOTIC), `WeaponSize`, `tier`, словарь `armor`
  (`base_ac`/`max_dex_bonus`/`acp`/`asf`) и `AcBonusType`
  (ARMOR/SHIELD/NATURAL/DEFLECTION/DODGE) — то есть типы урона, диапазоны крита,
  категории владения и стакинг бонусов AC из NWN2-брифа **уже есть**.
- Деньги: у героя своего кошелька нет; золото поселения двигается через
  `GameManager.modify_resource(&"gold", Δ)` — тот же путь, что у событий торговца
  (`resource_change.gold`, `crisis_event_system.gd:708`).
- Иконки артефактов: процедурный `gen_artifact_icons.gd` рисует форму **по слоту**,
  из-за чего 23 id делят одну картинку, а 6 id оружия не имеют файла вовсе
  (`docs/15-asset-spec-artifacts.md`). Конвейер генерации по id уже спроектирован в
  незаархивированном изменении `artifact-icons-comfyui` (capability
  `artifact-icon-generation`: ComfyUI → постобработка → автогейт канвас/вес/альфа/md5).
- Сейв версионирован: `SaveData.CURRENT_VERSION = 9`, цепочка `_migrate_vN_to_vN+1`.

## Goals / Non-Goals

**Goals:**

- Габарит предмета — данные, а не догадка интерфейса; одна точка правки.
- Рюкзак снаряжения конечен **по клеткам**, инвариант занятости проверяется тестом.
- Лавка, у которой есть покупательная способность (казна поселения) и продавец
  (`sell_artifact` получает вызывающего).
- Четыре предмета брифа с текстом владельца и числами только на читаемых ключах.

**Non-Goals:**

- Полный список из ~60 типов оружия, материалы (адамантин/мифрил/серебро/холодное
  железо), шкала зачарований +1/+2 и аффиксы («огненный», «вампирский»), крафт
  магических предметов — всё это отдельные изменения; здесь нет ни носителя, ни
  читателя у половины перечисленных полей.
- Броня и аксессуары сверх амулета и кольца; слоты плеч/рук/талии/ног уже есть в
  `Artifact.Slot`, но стока лавки их не касается.
- Весовая переноска (`weight-carry-system`) и рюкзак ресурсов (`hero-logistics`) —
  не трогаем: сетка относится только к рюкзаку снаряжения.
- Автопокупка, торг, репутация у купца, суточный ресток стоки.

## Decisions

**1. Габарит — поле предмета + таблица дефолтов по слоту.**
`Artifact.cells: Vector2i`, в `from_dict`/`to_dict`; если в данных не задан —
берётся из `SLOT_CELLS` (WEAPON→`2×3`, NECK→`1×2`, RING_*→`1×1`, …); не разрешается
— ошибка валидации каталога с id. *Почему не «габарит = слот»:* у оружия одного
слота разные формы — копьё `1×6` и лук `2×3`, иначе бриф невыполним. *Почему не
«по умолчанию 1×1»:* молчаливый дефолт прячет опечатку в данных ровно так же, как
немой ключ эффекта (Q-M79/D-197).

**2. Сетка 6×4 = 24 клетки.**
Шестиклеточная сторона — единственная, куда ложится `1×6` без поворота; 24 клетки
против прежних 16 предметов — осознанное ужесточение для длинного оружия. Число
идёт в реестр баланс-параметров (`docs/07-balance.md` §10), а не живёт константой
без адреса. *Альтернатива 8×3* — копьё влезает только горизонтально и рядов остаётся
три; *альтернатива «клетки = площадь, форма свободная»* — превращает «тетрис» в
счётчик и убирает единственную причину задачи.

**3. `backpack` остаётся списком предметов, к нему — массив размещений.**
`placements: Array[{artifact, origin: Vector2i, rotated: bool}]`, карта занятости
выводится. `backpack`-API и сигнал `backpack_changed` сохраняются как производные,
иначе правкой окажется каждый потребитель (экран, компонент, сейв, тесты).
*Альтернатива «словарь клетка→предмет»* — теряет форму предмета и ломает все
существующие вызовы.

**4. Деньги — золото поселения через `GameManager.modify_resource(&"gold", Δ)`.**
Тот же счётчик, что у событий торговца; новая сущность «кошелёк героя» — это новое
состояние, его миграция и ни одного второго потребителя. *Альтернатива — кошелёк:*
отклонена, пока лавка одна и герой один.

**5. Порядок сделки: место → деньги → списание → размещение.**
Отказ на любом шаге не меняет ни казну, ни сетку (спека `gear-merchant`). Размещение
выбирает первый подходящий прямоугольник детерминированным перебором, поворот
пробуется вторым — иначе «купил и не смог положить».

**6. Стока — данные, а не код: `game/data/config/merchant_stock.json`.**
Записи `{id, price_buy, price_sell}`; `price_sell` по умолчанию `value_gold / 2` и
проверяется гейтом на расхождение с данными предмета. *Альтернатива — зашить список
в скрипт экрана:* баланс правился бы в UI-коде.

**7. Вход в лавку — один: рынок города.**
Здание `market` уже есть (`MarketSystem.has_market`), экран поднимается из
`city_screen` и живёт в `world_ui.tscn` под `WorldUILayer` рядом с инвентарём.
*Почему не событие торговца:* у события `event_03_merchant.json` своя ставка
(ресурсы поселения), второй носитель той же лавки = два места правки цены.

**8. Числа предметов — только читаемые ключи; поэзия — в `description`.**
Из брифа механически выполнимы: копьё `+25 физ. урона` → `combat.damage_dice` /
`attack`, лук `+15% скорости атаки` → **читателя «скорость атаки» нет**, амулет
`реген 2 HP/сек` → читателя нет, кольцо `−20% оглушения` → читателя нет.
Решение: `description` получает flavor-текст владельца целиком, а в `modifiers` /
`combat` идут только ключи с существующим читателем (`attack`, `defense`,
`stack_hp`, `luck`, `morale`, `movement`, `spell_power`); текст про «шанс
отбрасывания» в описание не пишется, потому что игрок прочитал бы обещание без
исполнителя. *Альтернатива — добавить ключи «attack_speed», «regen», «stun_resist»:*
это не четыре строки, а приёмник в бою + тест на каждый; для четырёх предметов
лавки — неоправданный контур, заведено как отдельная задача (см. «Отложено»).

**9. Иконки — конвейером `artifact-icons-comfyui`, четыре файла.**
Тот же префикс-промпт [[13-art-bible]], канвас 64×64, PNG-32, ≤ 6 КБ, md5-уникальность.
*Альтернатива — процедурный `gen_artifact_icons.gd`:* он и есть причина дублей
«форма по слоту».

**10. Сцену правит генератор, не `.tscn`.**
`gen_inventory_scene.gd` — носитель `artifact_inventory_screen.tscn`; сетка
рисуется в генераторе (`GridCell_%d_%d`), ручная правка сцены будет стёрта следующим
прогоном. Для лавки генератор сцены заводится по тому же образцу.

**11. Миграция v9→v10: предметы старого рюкзака раскладываются по порядку, не
влезшие — в `overflow` («перевес»).**
Перевес — один массив в сейве + одна полоса в экране инвентаря, откуда предмет
можно надеть или продать. Рантайм в перевес не попадает: размещение отказывает
до списания денег. *Альтернатива «урезать старый рюкзак»:* молча потерять
снаряжение игрока.

## Risks / Trade-offs

- **[16 старых предметов × 6 клеток не влезают в 24 клетки]** → перевес + тест
  миграции на худшем случае; перевес виден игроку, ничего не теряется.
- **[Две модели ёмкости: клетки для снаряжения, вес для ресурсов]** → граница
  зафиксирована требованием «сетка не подменяет весовую переноску» и тестом
  «копьё в сетке не отнимает вес у ресурсов».
- **[Число клеток — баланс, а не догма]** → 24 в реестре `07-balance.md` §10;
  правка числа не должна трогать спеку (там только «конечная сетка»).
- **[Экран собирается генератором]** → все правки макета идут в
  `gen_inventory_scene.gd`; тест сверяет, что у сетки ровно 24 узла `GridCell_*`.
- **[Иконки зависят от чужого незаархивированного изменения]** → четыре иконки
  прогоняются тем же конвейером в этом изменении; при приезде
  `artifact-icons-comfyui` файлы просто совпадают по бюджету, конфликта нет.
- **[Новый экран = новый MCP e2e]** → путь сцены в нижнем регистре
  (`scenes/ui/merchant_screen.tscn`), иначе на Linux-раннере тест краснеет.
- **[Перевес — механизм ради миграции]** → минимален (массив + полоса) и остаётся
  полезным при любом будущем сжатии сетки; удалять его — значит вернуть риск потери
  предметов.

## Migration Plan

1. Поле `cells` + таблица дефолтов + валидация каталога (красный тест до данных).
2. Сетка в `HeroInventory` при сохранённом `backpack`-API; зелёные существующие
   тесты инвентаря — до новой логики размещения.
3. `CURRENT_VERSION = 10` + `_migrate_v9_to_v10` + roundtrip-тест и строка
   `SAVE_MATRIX` (сейф-путь закрывается до того, как лавка начнёт что-то покупать).
4. Экран инвентаря через генератор → кадр → ux-review зрением (AGENTS.md).
5. Лавка: данные стоки → экран → проводка к `modify_resource` → MCP e2e → кадр →
   ux-review.
6. Иконки → автогейт бюджета → кадр лавки с иконками → ux-review.
7. Публикация — локальный зелёный гейт + сводка + явное «мержи» владельца (D-224).
   Откат — откат коммита; миграция сейва односторонняя, поэтому шаг 3 обязателен
   до шага 5, а не после.

## Open Questions

- Точная форма сетки (6×4 против 6×5) — решается на ux-review по кадру: если
  длинное оружие в 4 рядах читается плохо, растёт число, а не структура спеки.
- Ресток стоки (суточный/статичный) — в MVP сток статичен; вопрос становится
  предметом, когда появится вторая лавка или редкость стоки.
