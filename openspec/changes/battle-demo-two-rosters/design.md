## Goals / Non-Goals

**Goals:**
- Один раз собрать конвейер «источник → кадр → аудит → спрайт → анимация → бой»,
  пригодный для повторного прогона без человека.
- Боевые правила проверяемы headless-тестом без сцены и без спрайтов.
- Состав боя — данные: новый набор без правок кода.
- Каждый визуальный вердикт оставляет в репозитории читаемый отчёт (пиксели в git
  не идут, отчёт и хэш кадра — идут).

**Non-Goals (дизайн-уровень, сверх скоупа из ТЗ):**
- Не делается general-ассет-пайплайн для основного проекта и не правится
  `scripts/concept_art/*`, `image-clone/*`, `game/**`.
- Не делаются: апскейл, SeedVR2, 3D-рендер позы, инверсная кинематика,
  автоматическая чистка пикселей, атлас-упаковка, компрессия под релиз.
- Не вводится второй тестовый фреймворк, свой CI, свой трекер.

## Decisions

### D1. Всё демо — в отдельном дереве `battle-demo/`
`battle-demo/{project.godot,assets,data,scenes,scripts,tests,tools,docs,artifacts}`.
Имена файлов ТЗ сохранены, префикс — свой.
**Почему:** три пути из ТЗ в корне уже заняты и перезаписались бы (см. Context);
`docs/` — Obsidian-хранилище с обязательным фронтматтером и гейтом
`check_docs_links.py`, отчёты демо попали бы в чужой граф.
**Альтернатива:** `docs/battle-demo/**` + `battle-demo-CHANGELOG.md` — больше
исключений в чужих гейтах, меньше выгоды.

### D2. Тесты — GdUnit4, не GUT
Копия `game/run_tests.sh` → `battle-demo/run_tests.sh` (GdUnit4 headless,
`Xvfb` на свободном дисплее по той же процедуре).
**Почему:** GUT — второй фреймворк, второй раннер, вторая точка отказа ради
демо; GdUnit4 уже аддон репозитория с обкатанным headless-запуском и политикой
кодов выхода (`0`/`101` = гейт зелёный, orphan — warning).
**Альтернатива:** GUT по тексту ТЗ — отклонена, отклонение фиксируется ADR в
`battle-demo/docs/decisions.md` (это и есть первый ADR, который требует ТЗ).

### D3. Генерация — новый `spec.json` для существующего `generate.py`
`python3 scripts/concept_art/generate.py --spec battle-demo/tools/spec.json
--variant demo_char`, вывод в `concept_art/demo_char/…` (вне git, как сейчас).
**Почему:** возобновляемость, затравка из id, повтор отказа, манифест и машинные
проверки уже написаны и обкатаны на 385 сюжетах; `--spec` — штатная точка
расширения (прецедент `qm89_spec.json`). Свой `variant` исключает пересечение с
идущим прогоном.
**Альтернативы:** форк `generate.py` (разъезд каноничного кода с чужого
прогона — отклонено); импорт `jobloop.py` с подменой `LAB` (чужой активный
файл, общий замок очереди — отклонено).
**Уточнение (2026-10-24, D13):** кадр рождается редактированием изображения, а
MCP-инструмент редактирования принимает один вход, поэтому вызов графа — свой
раннер `battle-demo/tools/gen_frames.py` (`POST /prompt` → `/history` →
`/view`). `spec.json` остаётся носителем состава прогона, сюжета, промпта и
затравки; `generate.py` не правится и остаётся путём чисто текстовых сюжетов.

### D4. Альфа — белый фон + `api_remove_background`, затем нарезка сеткой
Кадр генерируется на чистом белом фоне, фон снимает серверный
`api_remove_background` (rembg), результат — PNG 512×512 с альфой.
**Почему:** на пробном кадре edit-модели под ногами остаётся мягкая серая тень
непостоянного цвета, которую flood-fill по смежности от границ не берёт, а
rembg снимает фигуру одним вызовом того же MCP-сервера — нового кода нет.
**Фолбэк:** flood-fill **от границ** (внутренние белые пиксели живут) — если
rembg съест светлые участки (белая накидка, седая борода), кадр чистится им.
**Альтернатива:** нативная альфа модели — недоступна, выход модели RGB;
хрома-кей по магенте — ломает палитру, если модель не держит цвет фона.

### D5. Одна генерация = один лист поз 2×2, позы заданы сеткой карт
На анимацию генерируется лист 1024² с сеткой 2×2, режется на четыре 512² кадра.
Носитель поз — **то же полотно 2×2, только из DWPose-карт** (D14): в каждой
ячейке скелет нужной позы **этого персонажа** (D14), ячейки листа и ячейки
карты соответствуют друг другу, нарезка идёт по той же сетке.
**Почему:** 9 персонажей × 5 анимаций = **45 генераций ≈ 1 ч** вместо 180
одиночных кадров (≈ 3–4 ч серийной генерации), и персонаж внутри листа
держится лучше, чем в четырёх независимых прогонах. Аудит D6 отбраковывает
ячейки не по сетке — регенерируется только этот лист.
**Альтернатива, она же фолбэк:** одна карта — один кадр за прогон: в 4 раза
дольше, но поза каждой ячейки не зависит от того, поймёт ли модель сетку;
включается для конкретной анимации после двух отказов листа (см. Risks).
3D-поза — вне скоупа.

### D6. Аудит кадра — машинная проверка до просмотра
Порядок: размер/альфа/сетка/нейминг/дубликаты (PIL, падение за секунды) →
только прошедшие геометрию кадры попадают на стилевой просмотр read-агентом.
**Почему:** просмотр дорогого кадра, который не прошёл геометрию, — трата
итерации из трёх разрешённых.

### D7. Модель боя — чистые `RefCounted`, без `Node`
`CombatState` (юниты, очередь, фаза) + `UnitStats`/`Action`/`StatusEffect`/
`TurnQueue`; изменения — только через методы модели, наружу — сигналы
`turn_started`, `action_performed`, `unit_died`, `battle_ended`.
**Почему:** требование проверяемости без сцены (спека `turn-battle-core`);
сцены и спрайты — только читатель состояния.
**Альтернатива:** логика в узле `Battle.gd` — тесты вынуждены поднимать сцену,
headless-покрытие боевой математики вырождается.

### D8. Детерминизм: seed на бой, скриптованный ввод
`RandomNumberGenerator.seed` задаётся извне; тесты и съёмка скриншотов подают
действия списком. Один и тот же seed + тот же ввод → тот же бой.
**Почему:** без этого ни «детерминированного повтора» из спеки, ни воспроизводимых
кадров для приёмки UI, ни сравнения наборов A/B.

### D9. Анимации — `SpriteFrames` `.tres`, собираемый скриптом
`battle-demo/tools/build_sprite_frames.gd` обходит принятые PNG и пишет
`.tres` по одному на персонажа; руками не собирается. Зациклены `idle` и
`walk`; `attack`, `hit`, `turn` — однократные. Направление стороны — `flip_h`
в узле отображения, а не отдельные кадры. Гибель — `modulate` (обесцвечивание
и затемнение) поверх последнего кадра, отдельной анимации нет.
**Почему:** регенерация кадра не требует ручной правки сцен; имя файла —
единственный источник истины о листе/анимации/кадре; обесцвечивание даёт
«смерть» нулевой ценой в генерации (экономия 9 листов ≈ 20 % прогона).

### D10. read-агент = свежая сессия `pi` без инструментов
`pi -p --no-tools --no-session --mode text @<лист.png> "<бриф по чек-листу>"` —
готовый механизм `blind_judge.py`, отчёт → `battle-demo/docs/*-review-<дата>.md`
(файл, вердикт по файлу, отклонения, рекомендация, md5 просмотренного кадра).
Три итерации на файл, дальше — `battle-demo/docs/known-issues.md`.
**Почему:** независимость суждения и тот же прецедент в репозитории; md5 кадра
в отчёте — потому что пиксели в git не идут (D-185), а доказательство вердикта
остаться должно.
**Альтернатива:** тот же агент читает кадр своим vision-инструментом — работает
без отдельного процесса, но судит не независимо; оставлено как fallback, если
`pi` в окружении нет.

### D11. Скриншоты — один процесс GUI под `Xvfb` на свободном дисплее
`battle-demo/tools/capture_screens.gd` прогоняет состояния (выбор набора → старт
→ середина → результат) и пишет PNG в `battle-demo/artifacts/screenshots/`
(`gitignore` на пиксели, имена `<roster>_<state>.png`).
**Почему:** `--headless` в Godot 4 — dummy-рендер, настоящего кадра нет;
прецедент подъёма `Xvfb` и протокол «по одному процессу, чужие не трогать» —
`game/run_tests.sh` и AGENTS.md.

### D12. Цепочка скиллов — контракт исполнения, а не пожелание
`battle-demo/docs/agent-skills.md` — таблица «фаза → скилл → артефакт → чем
проверяется», заполняется из ТЗ §«Цепочка скиллов» и перечитывается в начале
каждой фазы. Отклонения — таблицей ниже, с причиной.

### D13. Идентичность персонажа — из пикселей источника, через qwen-image 2.1 edit
Внешность кадра НЕ описывается словами. Кадр редактируется из **кадра-источника
этого персонажа**: `TextEncodeQwenImage21` получает две картинки — портрет
(идентичность, костюм, стиль) и карту позы (D14) — и перекладывает персонажа в
позу. Граф (`POST /prompt`, проверен живым прогоном 2026-10-24: персонаж
источника встал в наведённую позу):

| Узел | Значение |
| --- | --- |
| `UNETLoader` | `qwen_image_2.1_int8_convrot.safetensors` |
| `CLIPLoader` | `qwen3vl_8b_int8_convrot.safetensors`, `type=qwen_image` |
| `VAELoader` | `qwen_image_2.1_vae_bf16.safetensors` |
| `QwenImage21Cache` | `device=auto`, `dtype=default` |
| `TextEncodeQwenImage21` | `images=[[портрет,0],[поза,0]]`, `resolution=0` |
| `KSampler` | `steps=25`, `cfg=1.0`, `euler`, `simple`, `denoise=1.0` |

**Почему:** прогон 45 листов по текстовому описанию (`krea2`, 2026-10-24) дал
правдоподобных, но **других** персонажей: модель никогда не видела источник и
рисовала нового человека в похожем снаряжении — лицо, пропорции, палитра и
детали костюма разошлись у всех девяти. Владелец путь отверг («создаёшь новых
персонажей, не похожих на референс»). Тот же кадр через edit-граф с портретом
источника даёт того же персонажа.
**Ловушки (проверено на сервере):**
- `qwen3.5_9b_qwen_image_2.1_pe_i2i*.safetensors` — **prompt-enhancer**, а не
  клип редактирования: с ним на выходе серый шум вместо кадра.
- MCP-инструмент `api_edit_image_qwen21` принимает **одно** изображение, вторую
  ссылку (карту позы) передать нельзя → только сырой `POST /prompt`.
- В API-формате autogrow-входы `TextEncodeQwenImage21` зовутся `images` (список
  ссылок), а не `image_1`/`image_2` — иначе `TypeError: unexpected keyword`.
- Части исходников нет в `input`-каталоге сервера (проверено по списку
  `LoadImage`) → недостающие грузит сам прогон (`POST /upload/image`).
**Промпт-контракт:** базовый промпт минимален и одинаков во всех прогонах —
`Transfer the pose from the second image to the character from the first image`.
Описание персонажа и стиля дописывается в промпт **по факту искажения**, а не
заранее: поплыли анатомия/костюм — добавляется описание персонажа из
`asset-spec.md`, поплыл стиль — стилевой контракт категории и
`photorealism, photograph` в negative.

**Альтернативы:** текстовое описание + стилевой эталон — пройдено, отвергнуто;
ControlNet-pose — на сервере только `control_v11p_sd15_openpose.pth`, под
qwen-image он не ставится, а `QwenImageDiffsynthControlnet` требует модель,
которой на сервере нет.

### D14. Поза кадра — скелетом этого персонажа, а не словами
Целевая поза задаётся изображением-скелетом (DWPose-вид: тело + кисти + лицо на
чёрном фоне) — вторым входом `TextEncodeQwenImage21`. **Скелет свой у каждого
персонажа:** карта извлекается из кадра-источника этого персонажа и правится
вручную так, чтобы сохранить его пропорции (телосложение, длина рук, ширина
плеч). Один скелет на нескольких персонажей не используется: скелет
коротышки-лучника, надетый на длинного воина, ломает пропорции обоих — модель
слушается скелета сильнее, чем референса.
**Откуда карты:** `python dwpose-cli.py <кадр-источник> --size 1024`
(`VisionEmbed-CLI`; пишет `dwpose_<имя>_openpose.png` плюс json с ключевыми
точками, квадрат 1024² на чёрном фоне). JSON и есть точка правки: точки
двигаются, скелет перерисовывается, поза кадра анимации получается **модификацией
позы источника**, а не рисованием с нуля. Карты — `battle-demo/assets/poses/`,
по одной на кадр (9 × 5 × 4 = 180), плюс лист-сетка 2×2 для D5.
**Почему не слова:** прогон 45 листов показал, что текстовое описание поз модель
усредняет — в `attack` четыре ячейки вышли одним и тем же замахом, в `idle`
четыре почти неразличимые стойки.
**Мелкие неточности** (палец лёг не туда, плечо уехало) правятся не
перегенерацией листа, а повторным редактированием конкретного кадра — тем же
графом, где первым входом идёт сам кадр.
**Альтернативы:** серверный `OpenposePreprocessor` (одна карта на всех) —
отклонена из-за пропорций; текстовое описание позы остаётся только для `turn`,
плюс `flip_h`.

**Отклонения от ТЗ (фиксируются ADR в `battle-demo/docs/decisions.md`):**

| Пункт ТЗ | Как делается | Причина |
| --- | --- | --- |
| GUT | GdUnit4 | D2: второй фреймворк в проекте |
| `docs/decisions.md`, `CHANGELOG.md`, `data/`, `project.godot` в корне | те же имена под `battle-demo/` | заняты; `docs/decisions.md` на case-insensitive FS = `docs/DECISIONS.md` |
| «read-агент (Explore/general-purpose)» | свежая `pi --no-tools` | в этой среде нет инструмента субагентов; прецедент `blind_judge.py` |
| свой CI/PR-контур | локальный гейт + push в `main` по «мержи» | AGENTS.md: CI агенту запрещён, PR не заводится (D-201, D-224) |
| `handoff`-скилл | `onboard` + `battle-demo/docs/handoff.md` | скилла `handoff` в этой установке нет |
| `setup-engine` поверх уже занятого движка | сверка версии + фиксация в `docs/architecture.md` | Godot 4.7 уже закреплён основным проектом |
| анимации `idle/walk/attack/hit/death` | `idle/walk/attack/hit/turn`, гибель без анимации | владелец, 2026-10-24: требуемый набор — «стоит / идёт слева направо / наносит удар / принимает удар / поворачивается» |

## Risks / Trade-offs

- **Общий ComfyUI занят чужим прогоном** → свой `variant`, последовательный
  прогон без параллелизма, возобновляемость по файлу, `--timeout 900`, запуск
  фоном; перед стартом — проверка, что очередь `image-clone` не блокирует сервер.
- **Общее дерево меняется под ногами** (уже было: HEAD сдвинулся, путь к
  генератору переехал) → все пути демо внутри `battle-demo/`, перед фазой —
  повторная сверка путей инструментов, чужие изменённые файлы не коммитятся.
- **Стилевой расхождение девяти персонажей** (прецедент: 6 осиротевших ролей —
  **0 из 6 приняты**) → генерация с референсом персонажа, стилевой гейт по
  контактному листу всех девяти, три итерации и далее `known-issues.md`, а не
  вечная правка.
- **Keying съедает светлые участки** (белая накидка, седая борода) → flood-fill
  только от границ, порог по смежности, визуальная проверка на просвет в
  отчёте; при дырах — регенерация кадра, а не ручная чистка.
- **Лист поз 2×2 не держит сетку** → аудит геометрии отбраковывает лист,
  повтор только этого листа; при двух подряд отказах — откат на покадровую
  генерацию для этой анимации (D5 fallback).
- **Edit-модель тянет кадр в фотореализм** (наблюдено 2026-10-24: тот же
  персонаж вышел фото-реенктором, когда в запросе не было стилевого контракта)
  → стилевой контракт категории и `photorealism, photograph` в negative едут в
  каждый edit-запрос; стилевой гейт D10 смотрит кадр источника рядом с кадром
  генерации, а не по памяти.
- **Лист не понимает сетку из четырёх карт позы** (позы поедут не по ячейкам) →
  проверка «какая поза в какой ячейке» по извлечённым ключевым точкам (D14);
  два отказа подряд — переход этой анимации на покадровую генерацию (фолбэк D5).
- **Правленый скелет разошёлся с пропорциями источника** (руки длиннее, плечи
  уже) → карта сверяется с источником по ключевым точкам json до прогона; кадр с
  уехавшими пропорциями — `fail` визуальной приёмки, карта правится, а не кадр.
- **`turn` — самый ненадёжный лист**: четыре стадии разворота в сетке модель
  держит хуже всего (велик риск четырёх разных поз вместо одного поворота) →
  меряется тем же аудитом геометрии и read-агентом; при двух отказах —
  упрощение до двух кадров разворота + `flip_h`, а не вечная правка.
- **Расход времени на генерацию** (45 листов ≈ 1 ч + повторы) → фон, пауза
  допустима, состояние — в манифесте `generate.py`.
- **UI-приёмка без человека рискует пропустить нечитаемость** → обязательный
  кадр-доказательство + вердикт по каждой AC в треде (урок UI-3 из AGENTS.md:
  фича пушится после ux-review, не до).

## Migration Plan

1. `battle-demo/` + `project.godot` + GdUnit4-аддон + `run_tests.sh` → зелёный
   пустой гейт.
2. Модель боя + тесты (без спрайтов) → покрыты спеки `turn-battle-core`.
3. Данные наборов + инварианты загрузки → `roster-lineups`.
4. Генерация 45 листов → keying → нарезка → аудит → `SpriteFrames` →
   стилевой отчёт.
5. Боевой UI + съёмка кадров + приёмка читаемости.
6. Дымовой прогон обоих наборов до экрана результата, `CHANGELOG.md`,
   `agent-skills.md` с отметками фаз, сводка в тред → по «мержи» push в `main`.

запись в `docs/mvp/TICKETS.md`, если появятся расхождения).
