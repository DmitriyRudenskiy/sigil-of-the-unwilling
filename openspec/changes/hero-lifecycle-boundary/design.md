# Design: hero-lifecycle-boundary

## Контекст

Система извлечена (R1), но «кто переподключает потребителей» и «кто владеет указателем
героя» не определены. Варианты, взятые из umbrella (IHeroConsumer) и из текущего
кода (Design D — статус-кво).

## D1. Механизм переподключения потребителей

Варианты:

- **A. `IHeroConsumer` (umbrella):** интерфейс `on_hero_changed(old, new)`, 9
  потребителей-классов, конформные тесты. Плюс: явный контракт, обнаруживаемость.
  Минус: 9 однострочных реализаций для присваивания поля; правки в 9 классах +
  3 тестовых файла (причина отсрочки Design D).
- **B. Реестр Callable (выбран):** `register_hero_consumer(func(hero): ...)`;
  координатор регистрирует; система прогоняет. Плюс: нулевой ceremony (8 из 9
  потребителей — просто `x.hero = h`), порядок = порядок регистрации (явный),
  тестируется фейковыми Callable без живых подсистем, новый потребитель — одна
  строка регистрации в WC, а не правка тела `_install_hero`. Минус: нет проверки на
  этапе компиляции (покрывается L2-тестом «каждый зарегистрированный потребитель
  получил нового героя» + L3 живой мир).
- **C. Сигнал `GameEventBus.hero_installed`:** плюс — самая слабая связь. Минус:
  порядок приёмки = порядок подключения (зависит от `_ready` — хрупко в headless),
  потребители обязаны быть в дереве на момент смерти, система привязывается к
  жизненному циклу шины.
- **D. Статус-кво (Design D):** 9 жёстких ссылок в `_install_hero`. Плюс: ничего не
  менять. Минус: причина этого change.

**Решение: B.** Реестр живёт в системе (система решает КОГДА), регистрация — в
координаторе (координатор знает СВОИ части). Направление знаний разведено:
«кто активен» — система, «кто потребляет» — координатор.

Форма записи реестра: `Array[Callable]`, каждый Callable принимает
`HeroController` (новый герой). Записи:

1. `battle_coordinator.hero = h`
2. `interaction_controller.hero = h`
3. `enemy_proc._hero = h`
4. `input_controller.hero = h`
5. `shortcuts._hero = h`
6. `event_router.hero = h; event_router._connect_hero_signals()`
7. `ui_manager._hero = h; ui_manager.ui.reattach_hero(h, camera)`
8. `inventory_screen.set_hero(h)`
9. `city_screen.hero = h`

(6/7/8/9 — составные лямбды; камера захватывается из `_camera` координатора.)

## D2. Владелец указателя активного героя

- **Статус-кво:** `WorldController._hero` (18 обращений внутри WC), система читает/
  пишет через `world.get_hero()/set_hero()` с guard'ом `has_method`.
- **Выбрано:** `HeroLifecycleSystem.active_hero` — единственный указатель.
  `WorldController.get_hero()` → `return _hero_lifecycle.active_hero`;
  `WorldController.set_hero(h)` → `_hero_lifecycle.install_hero(h)` (bootstrap).
  Прямые обращения к `_hero` внутри WC заменяются на `get_hero()`.
  Guard `has_method` исчезает — система самодостаточна.
- `world: Node2D` в системе остаётся: только как родитель для `add_child`
  (герой, DeathSequence, ChronicleScreen). Это parenting, не data flow — цикл
  по данным отсутствует.

## D3. Порядок операций в `install_hero`

Неизменён (регрессия ловится L3/L4):
`_active_hero` → `world.add_child` → `hero.city_manager` → `hero.setup(map_gen)` →
позиция → прогон реестра (порядок регистрации). «Убрать старого» (`_remove_hero`)
выполняется ДО установки нового, как сейчас (`_reincarnate`).

## Риски

- **Порядок потребителей:** если потребитель B зависит от A, регистрация должна
  отражать зависимость. Сейчас порядок в `_install_hero` работает — берём его как
  порядок регистрации (1→9 выше).
- **Лямбды и захват:** лямбды захватывают рефы подсистем по значению на момент
  setup; подсистемы на время забега не пересоздаются (bootstrap однократный) —
  безопасно.
- **3 тестовых файла:** стабы сейчас подменяют ПОЛЯ потребителей; после реестра
  часть подмен переезжает в «зарегистрируй фейковый Callable» (уменьшение объёма
  стабов, а не рост).
