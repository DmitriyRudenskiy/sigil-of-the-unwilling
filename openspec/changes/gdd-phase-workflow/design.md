# Design: GDD phase workflow

## Контекст

Метод задан владельцем как набор фаз с навыками. Реальность репозитория измерена
в `proposal.md`. Дизайн решает одно: **как взять метод, не сломав то, что уже
работает**. Три места, где метод и репо расходятся принципиально, и каждое требует
явного решения с отвергнутыми альтернативами.

## Решение 1 — реестры дополняются, нумерация не трогается

Метод просит `Q-<NN>`, `## D-<NN>`, `R-<NN>`. Репо несёт `Q-M##` (115 строк),
`D-1…D-269` в таблице из трёх колонок и ненумерованные риски.

**Решение:** идентификаторы остаются как есть, новая форма полей вводится
**для новых записей**, старые догоняются ratchet-бэклогом.

Отвергнуто:
- *перенумеровать `Q-M##` → `Q-##`*: 115 строк + сотни ссылок вида `Q-M82 → (б)`,
  `Q-M77 → (а)` в `DECISIONS.md` и `MVP-scope.md` становятся битыми; урок
  2026-10-24 (два тикета и два решения на одном номере из-за ручного
  перенумерования) стоит в `AGENTS.md` как запрет.
- *переписать `DECISIONS.md` под `## D-<NN>` с пятью полями*: 169 строк текста, в
  каждой — решения, отменять которые задним числом нельзя; дифф из 169 переписанных
  записей не ревьюится и означает, что ревью не пройдёт ничего вокруг.
- *оставить всё как есть*: тогда правило «⏳-решения, меняющие видение, — ⚑
  первыми» нечего применять, у него нет носителя (замер: `⏳` и `⚑` в реестре — 0).

**Носитель полей.** `DECISIONS.md` — таблица 3 колонки, поэтому статус и знак
пишутся **в начало третьей колонки**: `⏳ **Предварительное (рекомендация).** …`,
`⚑` — поверх `⏳`, если решение меняет видение. Поля «Отвергнутые:» и «Каскад:» —
той же третьей колонкой (сейчас 3 вхождения на 169 записей). Колонку не добавляем:
это переписывание всех 169 строк ради заголовка.

**R-##.** Риски получают номер при первой правке строки; новые обязаны его иметь.
Сверщик краснеет на риск без номера **только в newly-touched** строках — иначе
первая же проверка требует одновременно переписать 12 строк прозы.

## Решение 2 — состояния секций живут в frontmatter, гейт расширяется

`scripts/check_docs_links.py:26` знает семь статусов; `audited`, `verified`,
`locked` среди них нет, а `status: audited` **красит** прогон. Это единственная
точка, где метод и код конфликтуют напрямую, и решается она в коде: словарь
расширяется, `canon` (11 файлов) остаётся легаси-синонимом `locked`.

Машина состояний:

```
draft → audited → deepened → verified → locked
                     ↑  ↓ (новая дыра: verified → deepened)
locked → verified (ПЕРЕСМОТР дизайнера, обязателен D-### с основанием)
```

- Обратный переход **только** с записью в `DECISIONS.md`: откат состояния секции
  без решения — это тихая отмена чужой работы.
- Статусы не-GDD-ролей (`reference`, `snapshot`, `archived`, `redirect`) из
  машины исключены: 49 файлов с `status:` включают реестры, аудиты и банки,
  загонять их в `draft → locked` смысла нет.
- `verified*` (есть ⏳-решения) — **не** отдельное значение frontmatter, а
  производное: `status: verified` + наличие `⏳` в упомянутом `D-###`. Держать
  два описания одного факта — значит через месяц иметь противоречие.

## Решение 3 — ре-грундинг: дайджест вместо полного чтения

Метод: «каждый вход — перечитать ЦЕЛИКОМ». Замер: `docs/*.md` — 15 701 строка /
2,62 МБ; реестры — ещё 1,54 МБ; `TICKETS.md` — 0,80 МБ. Это за пределами любого
контекста, а имитация чтения («я помню») — ровно та причина, по которой контур
фаз 1–3 угас: теги `v3-grilled-pass3/4` есть, а `v4-locked` нет.

**Решение:** `scripts/gdd_grounding.py` печатает детерминированный дайджест —
счётчики состояний секций, открытые 🔴/🟡/🟢, хвост ⏳ и ⚑, последние N записей
каждого реестра, список секций, отстающих от своего статуса (например, `locked`
без `D-###`-основания), и ссылки на полные файлы. Лимит — 400 строк; если больше,
скрипт сам себя режет по приоритету (⚑ → ⏳ → 🔴 → остальное) и печатает счётчик
отброшенного.

Отвергнуто: *полное чтение* (физически невозможно, см. меру); *чтение по одному
файлу по запросу* (теряется именно то, ради чего ре-грундинг — противоречия между
секциями, которые поодиночке не видны).

## Решение 4 — навыки тонкие, носители уже существующие

Из 12 названных компетенций 6 есть как навыки, а `consistency-check` уже закрыт
сегодняшним `scripts/audit_docs_vs_code.py` (архивированная способность
`docs-code-sync`). Писать шесть новых навыков-пересказов — значит завести шесть
мест, где инструкция разойдётся с кодом (урок `docs-code-sync`: 40 битых ссылок
доков родились именно так).

## Решение 5 — верификация делится на машинную и ревью

Машинная часть (красная при провале): док-гейт связности, `audit_docs_vs_code.py`,
`gdd_gate.py` (состояния секций + поля новых записей + `blocked-on`), `0× TODO /
FIXME / ???` (сегодня — 0). Ревью-часть (не формализуется без потери смысла):
сходимость таблицы «источники/стоки» по каждой валюте × три стадии, достижимость
всех состояний конечных автоматов, покрытие трёх стадий прогрессии. Каждая строка
ревью-части в отчёте обязана иметь `[[секцию]]` и цитату; строка без доказательства
не выполняется, а уходит на доработку — это и есть шаг верификации метода.

Экономика: в `docs/06-economy.md` 14 табличных строк — таблицы есть, но покрывают
ли они все валюты × три стадии, машинно не проверяется без языка формул; поэтому
требование формулируется как «для каждой валюты реестра найдена строка в трёх
стадиях», а проверка — построчная, с цитатой.

## Решение 6 — теги фаз и правило «без СТОП»

`v1-audited`, `v2-deepened`, `v4-locked` заводятся как аннотированные теги с
путём к артефакту гейта в сообщении (существующие `v3-grilled*` — исторические,
не переименовываются). Правило «без СТОП» получает измеримый носитель: `[human]`
вопрос с применённой рекомендацией = запись `⏳` в `DECISIONS.md` + статус `⏳` в
`QUESTIONS.md`; «ОТВЕТ: Q-xx»/«ПЕРЕСМОТР: D-xx» из чата применяются **до** любой
новой работы (Шаг 0), а `gdd_grounding.py` поднимает ⚑-записи в дайджесте
первыми. Правил, запрещающих агенту работать дальше, в контуре нет ни одного.
