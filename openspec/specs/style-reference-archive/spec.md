# style-reference-archive Specification

## Purpose

Определяет единственный канонический комплект референсов стиля игры: его состав,
именование, карту-реестр в git и обязательные поля провенанса. Референсы — то,
куда смотрят художник и UI-фазы, поэтому комплект должен быть однозначным:
одновременно существует ровно один, и карта всегда описывает фактическое содержимое.

## Requirements

### Requirement: Единственный канонический комплект референсов
Проект SHALL содержать ровно один комплект референсов стиля, лежащий в каталоге
`reference/`. Комплект, объявленный владельцем каноническим, заменяет предыдущий
целиком: файлы вытесненного комплекта не остаются в проекте ни под каким именем
(в том числе «как доказательство отрицательного решения» — отрицательные решения
документируются текстом).

#### Scenario: Канонический комплект передан
- **WHEN** владелец передаёт новый комплект референсов и объявляет его каноном
- **THEN** файлы комплекта помещаются в `reference/` под каноническими именами
- **AND** файлы предыдущего комплекта удаляются из `reference/`
- **AND** ни один удалённый файл не возвращается в проект «на всякий случай»

#### Scenario: Отрицательное решение по вытесненному референсу
- **WHEN** документ стиля ссылается на референс, удалённый вместе с вытесненным комплектом
- **THEN** документ содержит формулировку решения (что отвергнуто и почему)
- **AND** не утверждает, что файл лежит в `reference/`

#### Scenario: Пиксели канона не попадают в git
- **WHEN** файл комплекта `reference/` не является картой `INDEX.md`
- **THEN** он не индексируется git (политика `reference/*` + `!reference/INDEX.md`)
- **AND** в сообщении коммита или в карте зафиксировано, где лежит пиксельный источник

### Requirement: Карта референсов
`reference/INDEX.md` SHALL быть единственным реестром комплекта и содержать по
одной строке на каждый файл комплекта. Обязательные поля строки: каноническое имя,
исходный файл (как передан владельцем), измеренные размеры/вес, категория,
«для чего» (какое решение стиля носитель), статус, провенанс/лицензия.

#### Scenario: Строка карты описывает файл комплекта
- **WHEN** читается строка карты `reference/INDEX.md`
- **THEN** файл с этим именем существует в `reference/`
- **AND** все обязательные поля строки заполнены (пустое поле недопустимо)

#### Scenario: Файл комплекта не описан в карте
- **WHEN** в `reference/` лежит файл, не упомянутый в карте
- **THEN** проверка согласованности падает с именем файла
- **AND** файл либо описывается строкой, либо удаляется

#### Scenario: Статус вне словаря
- **WHEN** в строке карты стоит статус, отсутствующий в словаре карты
  (`канон`, `pending`, `не стиль`, `уже в каноне`)
- **THEN** проверка согласованности падает

### Requirement: Провенанс каждого референса
Каждый файл комплекта SHALL иметь зафиксированные происхождение и лицензионный
статус. Файл, чьё происхождение не установлено, не может иметь статус `канон`
без явной пометки о непроверенности; файл, требующий атрибуции или платы,
получает строку с указанием условия.

#### Scenario: Носитель с непроверенными правами
- **WHEN** у файла комплекта происхождение или лицензия не подтверждены
- **THEN** строка карты содержит явную пометку «происхождение не проверялось»
- **AND** файл не используется как источник пикселя для `game/assets/` до закрытия вопроса

#### Scenario: Носитель с условием атрибуции или оплаты
- **WHEN** лицензия файла требует атрибуции либо платной подписки
- **THEN** строка карты называет условие и владельца права
- **AND** вопрос вынесен в реестр вопросов документации и в билет на приобретение

### Requirement: Проверка согласованности карты
Проект SHALL предоставлять запускаемую проверку, которая сверяет карту с диском:
имена файлов уникальны, каждая строка карты описывает существующий файл, каждый
файл каталога `reference/` (кроме самой карты) описан в карте, статусы взяты из
словаря карты. Проверка SHALL запускаться локально вместе с проверкой
связности документации и падать с ненулевым кодом возврата при расхождении.

#### Scenario: Дрейф комплекта против карты
- **WHEN** после смены комплекта карта и содержимое `reference/` расходятся
- **THEN** проверка завершается ненулевым кодом и печатает расхождение
  (строка карты без файла / файл без строки / нелегальный статус)

#### Scenario: Комплект и карта согласованы
- **WHEN** карта описывает ровно те файлы, что лежат в `reference/`
- **THEN** проверка завершается нулевым кодом и печатает число сверенных файлов

### Requirement: Эталон не переопределяется документацией

Конфликт между утверждением документации и каноничным эталоном SHALL решаться
в пользу эталона. Эталон не перерисовывается и не «улучшается»: по нему
выполняются только замеры (палитра, перспектива, свет, типографика), и он
используется как reference. Документ, противоречащий эталону, SHALL фиксировать
расхождение; замена — по политике снапшотов (`status: snapshot` на месте,
запись в `docs/DECISIONS.md` / `docs/CHANGELOG.md`), без перемещения файлов.

#### Scenario: Документ противоречит эталону
- **WHEN** утверждение из `docs/NN-*.md` расходится с эталоном из комплекта `reference/`
- **THEN** утверждение считается неверным, расхождение фиксируется в документе
- **AND** исправление — записью в `docs/DECISIONS.md` / `docs/CHANGELOG.md`

#### Scenario: Эталоном зовут не тот файл
- **WHEN** документ или тикет ссылается на файл, отсутствующий в карте `reference/INDEX.md`
- **THEN** ссылка признаётся устаревшей и удаляется или помечается вытесненной
- **AND** новый носитель не заводится «вместо» без решения владельца
